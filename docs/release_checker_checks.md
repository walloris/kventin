# Проверки release_checker.py

Документ описывает активные проверки, которые сейчас вызываются из `scripts/release_checker.py`.
Примеры ниже приведены в том же стиле, в котором сообщения попадают в консольный отчет и Jira-комментарий.

## Общий формат отчета

Ошибка:

```text
❌ [HRC-4360] [web][posts][neuro] После удаления поста пост не исчезает из виджета... (Иванов Иван Иванович)
   🔗 https://jira.sberbank.ru/browse/HRC-4360
   🔴 Story: отсутствует описание
```

Предупреждение:

```text
⚠️ [HRC-4360] [web][posts][neuro] После удаления поста пост не исчезает из виджета... (Иванов Иван Иванович)
   🔗 https://jira.sberbank.ru/browse/HRC-4360
   ⚠️  Zephyr: не удалось получить ТК (Read timed out)
```

Jira-комментарий содержит одну таблицу **«Объект релиза — Ошибки»**. Одна строка — одна задача со ссылкой и краткой темой, все её замечания собраны вместе без повторов. Общие ошибки относятся к самому релизу. Красная рамка, фон и текст означают неуспешную проверку; зелёные — успешную. Цвет оформляется wiki-макросами `panel` и `color`, без отдельного вступления и заключения.

В комментарии нет реестра этапов, времён, счётчиков, HTTP-кодов, endpoint, stack trace и диагностических подробностей. Техническая ошибка заменяется коротким сообщением о том, что не удалось проверить; исходная причина сохраняется в консоли и подробном отчёте. Необязательная диагностика GigaChat и Zephyr debug в комментарий не попадает. При успехе без замечаний остаётся строка релиза «Ошибок нет».

```text
|| Объект релиза || Замечания ||
| HRC-4360 — Проверка профиля | Нет описания. \\ Не найден ПР, связанный с задачей. |
```

## 0. Обязательный блокирующий SDD-гейт

Первым этапом в `release_checker.py` и `masked_release_cheker.py` запускается
`release-gate-sdd.mjs`, перенесённый из предоставленного файла побайтно, без правок.
Только код завершения 0 допускает остальные проверки. Любой другой код или ошибка
запуска блокирует релиз и немедленно останавливает проверки. Отчёт об отказе остаётся доступен.
Нет параметра отключения; гейт действует и для Hotfix, и при `--dry-run`.
Диагностические команды не являются проверкой готовности релиза.

Для развёртывания нужно положить `release-gate-sdd.mjs` рядом с Python-скриптом и
обеспечить `node` в PATH (с поддержкой встроенного `fetch`, Node.js 18+).
Python передаёт Jira URL и токен из своей конфигурации в `JIRA_BASE_URL` и
`JIRA_API_TOKEN` дочернего процесса. Токен не передаётся в аргументах команды.
DEBUG выключен, чтобы исходные HTTP-тела не попадали в диагностический вывод.

Особенности исходной логики, сохранённые без изменений:

- Проверяются до 200 напрямую связанных Story, без пагинации и фильтра по типу связи.
- Лейбл сравнивается с `sdd` без учёта регистра; буквальный `#SDD` не подходит.
- openspec ищется в файлах коммитов dev-status, а не в текущем дереве репозитория;
  совпадение ID префиксное (например, ST-1 может совпасть с ST-10).
- Отсутствие Story даёт код 0. Неопределённый openspec исключается из ошибок,
  даже если у этой Story отсутствует SDD. Поэтому обязательность гейта не означает
  блокировку этих случаев: изменение этого поведения потребует изменения исходной логики.
- До четырёх попыток detail с паузой 11 секунд перед каждой, последовательно для Story.
  Явного таймаута HTTP-запросов нет; выполнение может быть долгим.
- Требуется доступ к Jira search/issues и dev-status. Python-настройки TLS и прокси
  автоматически в Node.js не переносятся; корпоративный CA при необходимости задаётся
  через `NODE_EXTRA_CA_CERTS`. Ошибка подключения блокирует запуск остальных проверок,
  если исходный скрипт завершился ненулевым кодом.
- В исходнике обработка отсутствующих аргумента/токена обращается к DEBUG до его
  инициализации; это всё равно ненулевой код и блокировка. Общая диагностика аварий
  без DEBUG ограничена кодом завершения.

Упакованный `masked_release_cheker.py` содержит более старые остальные проверки;
в него добавлен только этот гейт, без замены остальных проверок современной версией.

## 1. Релизный тикет

Проверяется, что релизный тикет доступен по ключу.

Успех:

```text
Релизный тикет найден
```

Ошибка:

```text
Критическая ошибка: Не удалось получить тикет релиза: <текст ошибки>
```

## 2. Обязательный лейбл контура

Проверяется у самого релиза, каждой Story и каждого Bug/Defect/Ошибка.
Должен быть хотя бы один лейбл без учета регистра:

- `web`
- `back`
- `mobile`

Успех:

```text
Release: обязательный лейбл контура указан ✓
Story: обязательный лейбл контура указан ✓
Bug: обязательный лейбл контура указан ✓
```

Ошибка:

```text
Release: отсутствует обязательный лейбл контура. Должен быть один из: back/mobile/web
Story: отсутствует обязательный лейбл контура. Должен быть один из: back/mobile/web
Bug: отсутствует обязательный лейбл контура. Должен быть один из: back/mobile/web
```

## 3. Тип релиза Hotfix

Тип определяется по `customfield_23500`.
Если значение равно `Hotfix` без учета регистра, включаются hotfix-правила для багов.
Проверки ТЦ по КЭ для `web`/`back` выполняются только для обычных релизов, не для Hotfix.

Информационный вывод:

```text
🔥 Тип релиза: Hotfix — применяются дополнительные проверки
```

## 4. Сабтаска тестирования

У релиза ищется сабтаска, в названии которой есть `тестирование`.
В найденной сабтаске должно быть списанное время.

Успех:

```text
Затрекано 4.50ч
```

Ошибки:

```text
Сабтаска с 'Тестирование' не найдена
Нет затреканного времени
```

## 5. Артефакты релиза: комментарии тестировщика и списание времени

Для задач из состава релиза по связям `consist of` / `is part of` проверяется:

- есть комментарий от разрешенного тестировщика (включая Лакутина Романа Денисовича);
- у каждого тестировщика, оставившего комментарий, есть списанное время;
- если комментарий оставил Никонов Александр Алексеевич или Метляев Игорь Андреевич, списанное время от него не требуется;
- исключение по списанному времени не применяется для проектной области `HRC`;
- для Story время может быть списано в самой Story или в связанной тестовой Task.

Успех:

```text
Есть комментарии от: Симиник Даниил Григорьевич
У всех тестировщиков с комментариями, для которых требуется worklog, есть списанное время ✓
```

Ошибки:

```text
Нет задач со связью 'consist of' / 'is part of'
Нет комментариев от тестировщика
Нет затреканного времени от тестировщиков с комментариями: Симиник Даниил Григорьевич
Ошибка проверки артефактов: <текст ошибки>
```

## 6. Тестовое покрытие

Для задач состава релиза проверяется наличие прямо связанных ТК из `HRPQA` через Zephyr Scale Server/DC. JQL-функция Xray `hasTestCoverage()` больше не вызывается. Полученные ТК повторно используются для проверки Approved и вида тестирования.

Ошибка:

```text
Отсутствует тестовое покрытие (нет прилинкованных ТК)
```

Техническая ошибка, приводящая к `INCOMPLETE` обязательного этапа:

```text
Zephyr: не удалось проверить покрытие (<текст ошибки>)
Zephyr: не удалось подтвердить прямую связь с ТК: HRPQA-T12345
```

## 7. Zephyr: прилинкованные ТК у Story/Bug

Для задач из состава релиза проверяются прямые прилинкованные ТК в пространстве `HRPQA`.

Основной запрос — `GET /rest/atm/1.0/issuelink/{issueKey}/testcases` **без параметра fields**, как в версии до 08.10.2026. При недоступном endpoint, некорректном ответе или неполной странице используется `GET /rest/atm/1.0/testcase/search` с запросом `projectKey = "HRPQA" AND issueKeys IN ("HRC-4360")`, `startAt` и `maxResults=100`. Полный ответ issuelink по контракту API содержит все связанные ТК; резервный поиск читает все страницы. Проверяются ключи, формат ответа и продвижение пагинации. Неполный список не засчитывается как успешная проверка.

Полные данные из списка используются без дополнительных запросов деталей. Если нужных полей нет, выполняется `GET /rest/atm/1.0/testcase/{key}` без проекции полей. Поддерживается старый текстовый `id` вместо `key` в списках. Если ключ присутствует в ответе деталей, он должен совпадать с запрошенным; его отсутствие допускается при наличии содержательных полей ТК. Ошибки загрузки списков, деталей ТК/ТЦ и технически неуспешного поиска ТЦ не кэшируются как пустые данные. Прямая связь проверяется по полям связей; `HRC-4360` не совпадает с `HRC-43601`.

На поиск списка ТК одной задачи, включая резервный endpoint и все страницы, отводится 45 секунд. Одна серия запросов ограничена 32 секундами и максимумом `ZEPHYR_MAX_RETRIES_PER_REQUEST` попыток (по умолчанию 3), с прежним таймаутом 10 секунд на попытку. Паузы по умолчанию — 0,5 и 1 секунда. `Retry-After` действует и при переходе на резервный endpoint; превышающее бюджет ожидание не выполняется. TLS/401/403 прекращают обращения; прочие неуспешные серии учитываются в общем лимите Zephyr. Эти бюджеты ограничивают запросы и ожидания, но не являются жёстким таймаутом DNS и всего процесса.

Контракт endpoint, параметров `fields` и синтаксиса поиска сверяется с [официальной документацией Zephyr Scale Server/DC](https://support.smartbear.com/zephyr-scale-server/api-docs/v1/).

Проверки:

- все найденные ТК должны быть в статусе `Approved`;
- для `Bug` / `Defect` / `Ошибка` поле `Вид тестирования` должно быть `Регресс`;
- для `Story`, где `customfield_24000` = `Да`, поле `Вид тестирования` должно быть `Новый функционал`;
- для `Story`, где `customfield_24000` = `Нет`, поле `Вид тестирования` должно быть `Регресс`;
- ТК, которые пришли из контекста ТЦ/результата выполнения и не имеют прямой связи с задачей, пропускаются с предупреждением.

Успех:

```text
Zephyr ТК [HRPQA-T12345] в статусе 'Approved' ✓
Zephyr ТК [HRPQA-T12345]: Вид тестирования = 'Регресс' ✓
```

Ошибки:

```text
Zephyr ТК [HRPQA-T12345] «Проверка профиля»: не в статусе 'Approved' (текущий: 'Draft')
Zephyr ТК [HRPQA-T12345] «Проверка профиля»: 'Вид тестирования' = 'Новый функционал', ожидается 'Регресс'
Zephyr: задача есть в Jira, но нет прилинкованных ТК в пространстве HRPQA
```

Диагностика недоступных данных повышается до ошибки и `INCOMPLETE` в обязательном этапе. Пропуск неприменимых проверок и ТК без прямой связи остаётся предупреждением:

```text
Zephyr: нет задач со связью 'consist of' — проверка ТК пропущена
Zephyr: лимит неуспешных запросов исчерпан, дальнейшая проверка ТК пропущена
Zephyr: не удалось получить ТК (<текст ошибки>)
Zephyr ТК [HRPQA-T12345] «Проверка профиля»: не удалось получить детали ТК, статус проверяется по короткому ответу issuelink
Zephyr ТК [HRPQA-T12345] «Проверка профиля» пропущен: в данных ТК нет прямой связи с задачей HRC-4360; вероятно, ТК пришел из ТЦ/результата выполнения
Zephyr ТК [HRPQA-T12345]: не удалось проверить поле 'Вид тестирования' — не найдено в кастомных полях ТК
Zephyr ТК [HRPQA-T12345]: не удалось определить статус ТК
Zephyr ТК [HRPQA-T12345]: не удалось получить детали ТК для проверки поля 'Вид тестирования'
```

## 8. Back release: обязательные ТЦ по КЭ

Проверка выполняется только для обычного релиза, не Hotfix, если у релиза есть лейбл `back`.

Для каждой КЭ сервиса из Story/Bug состава релиза должны быть ТЦ:

- `{ключ релиза}.{КЭ сервиса}.ipad/pwa/safari/sberbrowser.Регресс`;
- `{ключ релиза}.{КЭ сервиса}.api.Регресс`;
- если внутри КЭ есть Story с `Новая функциональность = Да`, дополнительно `{ключ релиза}.{КЭ сервиса}.api.НФ`.

Название ТЦ матчится мягко: без учета регистра, лишних пробелов, ID КЭ в скобках, русских/английских алиасов `Регресс`/`Regress`/`Regression`, `НФ`/`NF`, а также допускается дата в конце названия.

Успех:

```text
Back release: для КЭ 'CoreTech(7993288)' найден iPad/PWA/Safari/SberBrowser Регресс ТЦ [HRPQA-C133028] 'HRPRELEASE-131571.CoreTech(7993288).ipad/pwa/safari/sberbrowser.Регресс' ✓
Back release: для КЭ 'CoreTech(7993288)' найден API Регресс ТЦ [HRPQA-C133029] 'HRPRELEASE-131571.CoreTech(7993288).api.Регресс' ✓
Back release: для КЭ 'CoreTech(7993288)' найден API НФ ТЦ [HRPQA-C133030] 'HRPRELEASE-131571.CoreTech(7993288).api.НФ' ✓
```

Ошибки:

```text
Back release: не удалось определить Jira field id для поля КЭ/КЭ сервиса
Back release: ошибка получения задач состава релиза для проверки КЭ: <текст ошибки>
Back release: не заполнено поле КЭ сервиса (customfield_xxxxx); невозможно проверить обязательные API ТЦ
Back release: в составе релиза не найдено ни одной Story/Bug с заполненной КЭ сервиса
Back release: Zephyr не вернул ТЦ по ключу релиза HRPRELEASE-131571
Back release: для КЭ 'CoreTech(7993288)' (HRC-4360) отсутствует ТЦ Zephyr по маске 'HRPRELEASE-131571.CoreTech(7993288).api.Регресс'
Back release: для КЭ 'CoreTech(7993288)' есть Story с 'Новая функциональность' = 'Да', но отсутствует ТЦ Zephyr по маске 'HRPRELEASE-131571.CoreTech(7993288).api.НФ'
```

Предупреждения:

```text
Back release: нет задач со связью 'consist of' — проверка API ТЦ по КЭ пропущена
Back release: Zephyr временно не отдал ТЦ по ключу релиза HRPRELEASE-131571; проверка ТЦ пропущена, отсутствие ТЦ не зафиксировано как ошибка
```

## 9. Web release: обязательные ТЦ по КЭ

Проверка выполняется только для обычного релиза, не Hotfix, если у релиза есть лейбл `web`.

Для каждой КЭ сервиса из Story/Bug состава релиза проверяются:

- если внутри КЭ есть Story с `Новая функциональность = Да`, нужен `{ключ релиза}.{КЭ сервиса}.ipad/pwa/safari/sberbrowser.НФ`;
- для проекта `NEUROUI` у НФ нет PWA: `{ключ релиза}.{КЭ сервиса}.ipad/safari/sberbrowser.НФ`;
- всегда нужны регресс-ТЦ:
  - `{ключ релиза}.{КЭ сервиса}.ipad.Регресс`;
  - `{ключ релиза}.{КЭ сервиса}.pwa.Регресс`;
  - `{ключ релиза}.{КЭ сервиса}.safari.Регресс`;
  - `{ключ релиза}.{КЭ сервиса}.sberbrowser.Регресс`;
- для проекта `NEUROUI` регресс PWA не требуется.

Успех:

```text
Web release: для КЭ 'SmartProfile(2295205)' найден ipad Регресс ТЦ [HRPQA-C133028] 'HRPRELEASE-130030. SmartProfile(2295205). iPad. Регресс' ✓
Web release: для КЭ 'HRP.CoreUI-Neuro(9644020)' найден iPad/Safari/SberBrowser НФ ТЦ [HRPQA-C133029] 'HRPRELEASE-131704. HRP.CoreUI-Neuro(9644020). iPad/Safari/SberBrowser. НФ' ✓
Web release: КЭ 'HRP.CoreUI-Neuro(9644020)' относится к NEUROUI — PWA ТЦ не требуется ✓
```

Ошибки:

```text
Web release: Zephyr не вернул ТЦ по ключу релиза HRPRELEASE-130030
Web release: для КЭ 'SmartProfile(2295205)' есть Story с 'Новая функциональность' = 'Да', но отсутствует ТЦ Zephyr по маске 'HRPRELEASE-130030.SmartProfile(2295205).ipad/pwa/safari/sberbrowser.НФ'
Web release: для КЭ 'SmartProfile(2295205)' (SFILE-11765, SFILE-11771) отсутствует ТЦ Zephyr по маске 'HRPRELEASE-130030.SmartProfile(2295205).ipad.Регресс'
```

Предупреждение:

```text
Web release: Zephyr временно не отдал ТЦ по ключу релиза HRPRELEASE-130030; проверка ТЦ пропущена, отсутствие ТЦ не зафиксировано как ошибка
```

## 10. Zephyr: проверки найденных ТЦ

Для каждого обязательного ТЦ, найденного в back/web-проверках, дополнительно проверяется:

- поле ТЦ `Вид тестирования`;
- все ТК внутри ТЦ находятся в статусе `Approved`.

Если ТЦ найден по маске `.НФ`, ожидается `Вид тестирования = Новый функционал`.
Если ТЦ найден по маске `.Регресс`, ожидается `Вид тестирования = Регресс`.

Успех:

```text
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': Вид тестирования = 'Регресс' ✓
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': все ТК внутри ТЦ в статусе 'Approved' ✓
```

Ошибки:

```text
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': не удалось получить детали ТЦ для проверки поля 'Вид тестирования'
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': поле 'Вид тестирования' не найдено, ожидается 'Регресс'
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': 'Вид тестирования' = 'НФ', ожидается 'Регресс'
```

## 19. Наличие Pull Request — неблокирующая проверка

Для каждой Story/Bug/Defect/Ошибка в составе релиза выполняется поиск Pull Request. Если PR не найден или API недоступен, результат — предупреждение у этой задачи, без блокировки выпуска.

Для Story проверяется только сама Story. PR в Task внутри Story не засчитывается для этой проверки.
Для Bug/Defect/Ошибка проверяется сама задача.

Проверка ищет связь Jira → PR с резервными источниками из версии до 08.10.2026:

1. Запрашивается `dev-status/latest/issue/summary`. Положительный целочисленный `summary.pullrequest.overall.count` сразу подтверждает наличие PR — один запрос.
2. Версия `1.0` используется только при недоступном или неполном ответе `latest`.
3. Проверяются Jira remote links с явной ссылкой на PR.
4. Если связь не подтверждена, запрашивается `dev-status/issue/detail` для `pullrequest`, затем `repository` (только явные PR-объекты или ссылки). При недоступной summary или отсутствии данных об интеграции используются прежние `stash`, `bitbucket`, `bitbucket-server`; при рабочей summary — указанные ею интеграции. Поддерживаются `latest` и `1.0`. На первом подтверждённом ПР поиск останавливается.
5. Последний резерв — свойства самой Jira-задачи с именами development/dev/stash/bitbucket/pull/vcs, максимум три подходящих свойства. Коммиты, пустые метаданные репозитория и ПР дочерней Task не засчитываются за ПР Story.

Нулевой счётчик вместе с успешным ответом remote links без PR означает «PR не найден». Таймаут, отсутствие счётчика и неполный ответ означают «не удалось подтвердить PR»; оба случая остаются неблокирующим замечанием. При отсутствии других замечаний комментарий зелёный и запуск успешен, но в строке задачи явно указано, что PR не найден или не проверен.

HTTP-запрос деталей имеет socket timeout до 12 секунд вместо добавленных сегодня 3 секунд; серия — до 25 секунд. Для прочих PR-запросов сохранены 3 секунды на попытку и 12 на серию. Максимум **три попытки** при сетевых сбоях, HTTP 408/429/500/502/503/504, ошибках JSON или прикладных ошибках Jira; паузы 0,5 и 1 секунда. `Retry-After` (секунды или HTTP-дата) общий для источников ПР и сохраняется между этапами; если ожидание не помещается в бюджет, дальнейший запрос не выполняется. Ошибки TLS/401/403 не повторяются.

Успешные ответы сохраняются на запуск релиза. Временные ошибки и отключение источника после трёх неудачных серий истекают через 15 секунд; новый этап ПР может повторить временно неуспешные чтения, сохраняя Retry-After и запрет повторов TLS/401/403. Бюджет отдельного поиска — 30 секунд; каждый из этапов обязательного PR, merged PR и GigaCode имеет отдельный бюджет 120 секунд. В проверке наличия ПР сводке выделяется до 5 секунд, remote links — до 4, деталям — до 16, чтобы осталось время на свойства задачи. При исчерпании бюджета новые HTTP-запросы не начинаются; это не ограничение длительности всей джобы и не жёсткий wall-clock timeout DNS/сетевого стека.

Для merged запрашивается только `pullrequest`. Для GigaCode проверяются `pullrequest`, `repository`, `commit`; первый найденный маркер GigaCode достаточен, остальные источники не запрашиваются. При уже установленном AIFIXED запросы не нужны. Эти проверки также работают с прямыми endpoint интеграций при недоступной summary. Недоступность merged-проверки — неблокирующее предупреждение; подтверждённый merged PR у исключённой задачи остаётся ошибкой; недоступность GigaCode — предупреждение без ложного сообщения об успешной проверке.

Успех:

```text
Pull Request найден в HRC-4360 (Jira development: связанных PR — 2) ✓
```

Ошибка:

```text
Pull Request не найден. Для каждой Story/Bug в составе релиза должен быть PR на самой задаче
```

Предупреждение:

```text
Pull Request: не удалось проверить HRC-4360: <текст ошибки>
```

## 29. Контроль полноты и диагностика джобы

Каждый запуск формирует реестр из 16 этапов. Для каждого в консоли немедленно печатаются START, итоговый статус, время, число объектов и количество успешных результатов, ошибок и предупреждений. Строки выводятся без буферизации. Этот диагностический реестр остаётся в логе; в Jira публикуется краткая цветная таблица объектов и замечаний, описанная в начале документа. Текст из задач экранируется, включая разделители таблицы, wiki-макросы и переносы строк в HTML-энтити.

- PASS — есть успешные результаты, нет ошибок/предупреждений.
- FAIL — найдены нарушения правил.
- INCOMPLETE — нет необходимых данных либо этап завершился технической ошибкой. Для обязательного этапа это блокирующая ошибка; неполученный PR, GigaCode и GigaChat сохраняют рекомендательный статус. Подтверждённый merged PR у исключённой задачи остаётся блокирующим нарушением.
- WARN — этап дал предупреждения.
- SKIP — этап неприменим по явному условию (например, нет web/back либо релиз Hotfix); причина указана.
- NO_FINDINGS — этап завершился без зарегистрированных результатов. Это не утверждение, что объекты были проверены: применимых объектов может не быть.

Необработанная ошибка одного этапа не прерывает последующие этапы. Обязательные проверки, которым не удалось получить данные, не маскируются под успех. Все Jira-поиски получают полные страницы результатов (`maxResults=False`); одинаковые успешные чтения задач, комментариев, worklog, полей и поисков кэшируются в пределах запуска. Запись и ошибочные SDK-запросы не кэшируются. Новый запуск очищает оперативные кэши.

В логе #1452 от 08.10.2026 Zephyr не выполнил проверки ТК/ТЦ из-за повторных `CERTIFICATE_VERIFY_FAILED`: 20 неуспешных запросов, каждый с ретраями. После ошибки поиска запускался ещё и перебор номеров ТЦ. Комментарий скрывал эти предупреждения. Исправления: явная единая настройка TLS для Jira/Zephyr, отсутствие ретраев при ошибке сертификата/401/403, прекращение резервного сканирования при TLS/401/403 или исчерпании лимита ошибок, видимые INCOMPLETE и предупреждения в комментарии. Причина недоступности PR теперь выводится отдельно: TLS, timeout, HTTP-код, ошибка JSON/API; по старому логу установить её однозначно нельзя.

В логе #1455 обнаружены таймаут покрытия через Xray, таймаут metadata полей Jira с повторным использованием пустого кэша и HTTP 429 при проверке PR. При этом сами ТК были получены (35 кейсов), проверка наличия ПР прошла для 9 задач, а проверка ТЦ останавливалась на metadata КЭ. Текущий код читает metadata с тремя ограниченными попытками (до 15 секунд на запрос, 35 секунд на серию), неудачный результат не сохраняется в кэш полей или сервисов. Таймаут чтения Jira SDK увеличен с добавленных сегодня 10 до 30 секунд. Для ТК внутри ТЦ сообщение «все Approved» выводится только при успешной проверке каждого ТК. Несоответствия вида тестирования остаются ошибками качества данных и требуют исправления в Zephyr.

Сравнение с последней версией до сегодняшних изменений (`8a758d6`): в `f38c5e1` удалили прямое чтение ПР без summary и свойства Jira, сократили таймаут деталей с 30 до 3 секунд и ввели кэш неуспеха на весь запуск. В `5ed6b5f` добавили проекцию полей Zephyr, отвергли текстовый `id` ТК и ответы деталей без `key`, ограничили серию Zephyr 12 секундами вместо прежних трёх попыток по 10 секунд. Восстановлены прежние совместимые запросы и резервные источники; ограничения общего времени, строгая проверка свидетельств ПР и различение ошибок API/отсутствия данных сохранены. Совместимость проверяется синтетическими ответами, включая локальный HTTP-сервер с задержкой детали ПР 3,2 секунды. Без актуального лога после `5ed6b5f` нельзя приписать конкретный сбой рабочего сервера одной из этих причин.

TLS-настройки:

- `RELEASE_CHECKER_CA_BUNDLE=/path/to/corporate-ca.pem` — использовать корпоративный CA bundle;
- `RELEASE_CHECKER_VERIFY_SSL=1` — включить проверку стандартным хранилищем доверия;
- без этих переменных сохраняется прежняя политика скрипта `verify=False`, теперь передаваемая явно, чтобы `REQUESTS_CA_BUNDLE` не меняла её неявно. Автоматического отключения TLS-проверки после ошибки нет.

Для диагностики каждого HTTP-запроса включить `RELEASE_CHECKER_DEBUG_HTTP=1`. Лог содержит путь endpoint, безопасные параметры идентификации Jira, номер попытки, результат и длительность; заголовки авторизации и тела ответов не выводятся. Медленные и неуспешные запросы логируются и без этой переменной.

Пример запуска в окружении джобы без записи комментариев и лейблов:

```bash
RELEASE_CHECKER_DEBUG_HTTP=1 python -u scripts/release_checker.py --dry-run HRPRELEASE-146076
```

`--dry-run` выполняет чтение и проверки, выводит требуемые изменения AIFIXED, но не применяет их. Код выхода 1 сохраняется при нарушениях обязательных проверок. Этот режим использует реальные сервисы; локальные тесты работают на синтетических ответах и не публикуют данные в Jira.

## 32. Диагностика PR/ТЦ и комментарий от 18.10.2026

Изменения не увеличивают существующие сетевые бюджеты:

- PR: 30 секунд на задачу, 120 секунд на этап. Внутри 5 секунд поиска summary одна попытка теперь может ждать до 5 секунд вместо 3. Это позволяет получить медленный успешный ответ, не расходуя время на повтор. В detail оставшееся время делится между запрошенными типами данных: зависший `pullrequest` больше не вытесняет `repository`/`commit`. В проверке наличия PR общий бюджет detail остаётся 16 секунд. Не начатые из-за исчерпания бюджета запросы не попадают в кэш ошибок и не отключают источник для следующих задач.
- ТЦ: общий бюджет поиска остаётся 45 секунд. На issuelink и индекс проекта вместе отводится максимум 25 секунд, на Jira metadata — максимум 8 секунд; оставшееся время доступно прямому поиску/кэшу. Неиспользованное время остаётся в общем бюджете. Быстрые временные ошибки issuelink допускают повтор в пределах прежних 10 секунд, вместо немедленного перехода к широкому поиску. Значения приведены для настроек по умолчанию.
- Не более трёх попыток PR и `ZEPHYR_MAX_RETRIES_PER_REQUEST` попыток Zephyr (по умолчанию 3). Паузы, `Retry-After` и все резервные источники учитывают общий дедлайн. TLS и ошибки прав не повторяются. Существующие ограничения количества страниц, сканирования и неуспешных запросов сохранены.

Это лимиты сетевых ожиданий и запуска следующих запросов, а не жёсткий таймер процесса: DNS, загрузка тела ответа, Jira SDK, прочие проверки и запись логов могут занимать дополнительное время. Не доказано, что реальный запуск стал быстрее или что рабочий сервер перестал отдавать таймауты; это проверяется по следующему запуску. Реальные API при локальной проверке не вызывались.

### Запуск для разбора

**Промежуточная версия для Jenkins:** подробная диагностика включена по умолчанию параметром `HTTP_DEBUG_ENABLED = True` в начале `scripts/release_checker.py`. Запускайте существующую джобу как обычно, без изменения Jenkins-скрипта. События `[HTTP DEBUG]` и итоги проверок появятся в Console Output; для анализа достаточно прислать этот вывод. Обычная публикация комментария и обновление AIFIXED сохраняются, если команда не содержит `--dry-run`.

Чтобы выключить подробную диагностику, установите `HTTP_DEBUG_ENABLED = False`. При необходимости переменная окружения `RELEASE_CHECKER_DEBUG_HTTP=0` или `1` переопределяет параметр в коде. Явное выключение отключает подробные события и в консоли, и в JSONL-файле; обычные сообщения об ошибках и результатах остаются. Строка `[DIAGNOSTICS] HTTP=ON/OFF` в начале запуска показывает выбранный режим. Если задан `RELEASE_CHECKER_HTTP_LOG`, включённая HTTP-диагностика записывается в этот файл вместо консоли.

Для отдельного локального запуска с сохранением файлов:

В окружении с обычной конфигурацией Jira и зависимостями выполните команду ниже, заменив `HRPRELEASE-123456` нужным ключом. Запускайте из корня репозитория; интерпретатор можно заменить на используемый в джобе.

```bash
RELEASE_CHECKER_HTTP_LOG=release-http.jsonl \
RELEASE_CHECKER_COMMENT_PREVIEW=release-comment.wiki \
python scripts/release_checker.py --dry-run HRPRELEASE-123456
```

Пришлите `release-http.jsonl` и, для оценки комментария, `release-comment.wiki`. В режиме `--dry-run` комментарий не публикуется, старые комментарии не удаляются, AIFIXED не проставляется. Локальный кэш ТЦ по-прежнему может обновляться. Код выхода 1 означает, что найдены замечания, блокирующие релиз; это само по себе не означает падение скрипта.

JSONL содержит время UTC, источник, путь без query string, разрешённые параметры, идентификатор запроса, номер попытки, выделенный таймаут, остаток бюджета, HTTP-статус, длительность, размер тела, тип содержимого, причину повтора и длительность паузы. Для JSON сохраняется ограниченная структура известных полей и размеры коллекций, без значений названий, описаний, токенов, cookies, заголовков авторизации и сырых тел. В лог попадают также чтения кэша PR, отключение источника после ошибок, итог поиска ТЦ и итоги этапов. Если JSON не разобран, остаются HTTP-статус, тип содержимого и тип исключения. Jira SDK и старые отдельные `--diag-*` не являются частью этого HTTP-трейсинга; старые диагностические режимы могут печатать сырые данные, поэтому для первого разбора используйте команду выше.

Файл JSONL дополняется при повторном запуске. Без `RELEASE_CHECKER_HTTP_LOG` подробные события выводятся в консоль при включённом `HTTP_DEBUG_ENABLED` или `RELEASE_CHECKER_DEBUG_HTTP=1`. `RELEASE_CHECKER_COMMENT_PREVIEW` сохраняет текст только в `--dry-run`.

### Внешний вид комментария

Над таблицей — краткие счётчики «Исправить / Нет данных / Проверить». В таблице три колонки: объект со ссылкой, статус с Jira-иконкой и нумерованные замечания. «Нет связанных тест-кейсов» отличается от «Не удалось проверить тест-кейсы». Для недоступных данных есть пояснение о повторном запуске. Диагностика HTTP остаётся в логах.

[Пример wiki-комментария](release_checker_comment_example.wiki) с вымышленными задачами сгенерирован текущей функцией форматирования.

Зелёный результат при неблокирующих PR-замечаниях сохраняется, но заголовок прямо сообщает об этих замечаниях. Другие правила блокировки и цвета сохранены. Распознаются старые комментарии с таблицей из двух колонок. Совпадение отпечатков запроса и отрицательного контроля помогает обнаружить игнорирование фильтра. Найденные циклы не означают, что получен полный список.

Локальные тесты используют имитацию ответов; доступность маршрутов в корпоративной сети должен подтвердить Jenkins.

### Маски ТЦ и соответствие КЭ (21.10.2026)

Для регрессионных web-циклов `WEB` принимается как вариант канала `SberBrowser`, в том числе для NEUROUI. Остальные поддерживаемые каналы и правила обязательности сохраняются. Для сопоставления имени КЭ с названием ТЦ также допускается значение Jira с префиксом `CI…`: например, `CI01234567 HRP.CoreUI-Dates`. Ключ релиза и само имя сервиса по-прежнему должны совпадать.

Добавлен независимый обязательный этап «Совпадение КЭ задач и релиза». Каждая КЭ каждой задачи состава релиза (`consists of`/`is part of`) должна присутствовать среди КЭ релиза; дополнительная КЭ релиза не является ошибкой. При сравнении КЭ учитываются регистр и пробелы вокруг точек. Если обе стороны содержат CI-код, сравниваются коды. ### Отдельный процесс определения GigaCode / AIFIXED

Проверка GigaCode больше не зависит от общего метода, который возвращает все development-данные либо одну объединённую ошибку. Новый `_lookup_gigacode` возвращает FOUND / NOT_FOUND / UNKNOWN с результатами отдельных источников. Совместимый внешний метод по-прежнему возвращает маркер или сигнализирует о неполных данных. Наличие PR и проверка merged PR используют прежние методы.

- FOUND: маркер найден в объекте PR или коммита. Ошибка другого источника не отменяет положительное доказательство. Положительный результат переиспользуется в пределах запуска, в том числе во время серверной паузы.
- NOT_FOUND: проверенные текстовые поля не содержат поддерживаемого маркера, либо summary явно сообщает нулевые количества. Это отсутствие маркера в доступных метаданных, а не доказательство того, что автор не применял ИИ.
- UNKNOWN: источник недоступен, не хватает объектов относительно summary, отсутствуют текстовые поля, данные помечены как неполная страница, структура не поддержана или бюджет исчерпан. UNKNOWN не кэшируется как отсутствие маркера.

Для каждого типа данных выделяется часть оставшегося бюджета; внутри неё резервируется время альтернативным провайдерам и версиям API. Нулевые источники из summary не запрашиваются. Если коммиты уже прочитаны через repository и summary не сообщает отдельного количества commit, повторный поиск тех же данных через неподдерживаемые commit-алиасы не требуется. Общие 30 секунд на задачу и 120 секунд на этап, серверный Retry-After и ограничения попыток сохранены.

Маркеры ищутся только в объектах PR/коммитов, а не в служебном имени провайдера или тексте ошибки. Если одна связанная Task недоступна, но другая подтверждает GigaCode, предупреждение о неопределённом результате для всей Story не публикуется. Ошибка чтения первой Task остаётся в логах.

При включённой HTTP-диагностике строки `[GIGACODE]` в Jenkins содержат ключ задачи, время, тип данных, провайдера, версию API, количество объектов, наличие текстовых полей (без их содержимого), признаки неполноты, причину пропуска и итоговый verdict. HTTP-лог отдельно показывает попадание в кэш, отключение источника после сбоев, статусы и таймауты. Ошибки внутри HTTP 200 классифицируются отдельно от некорректного JSON: upstream_timeout / permission / connection / application_link / rate_limit / unclassified. Сырые сообщения сервера, тексты PR/коммитов и токены не печатаются.

Тексты комментария Jira не изменены. Подробная диагностика не добавляется в комментарий или его таблицу. Для проверки результата нужен обычный запуск Jenkins с включённым HTTP_DEBUG_ENABLED или RELEASE_CHECKER_DEBUG_HTTP=1; локальные тесты не подтверждают доступность корпоративных сервисов.

### Резервный поиск ТЦ через API фронта Zephyr

При неполном или технически неуспешном основном поиске используется
`GET /rest/tests/1.0/testrun/search`, по контракту из браузерного запроса:
`results`, `total`, `startAt`. Поиск охватывает проект целиком без фильтра
выбранной в браузере папки; ключ релиза сопоставляется с названием ТЦ с
проверкой границ (`REL-1` не совпадает с `REL-10`). Связи с Jira в этом
ответе отсутствуют: этот путь предназначен для ТЦ с ключом релиза в имени.
Детали и проверки найденных ТЦ остаются в существующем процессе.

Проект по умолчанию — `88701` (HRPQA из предоставленного запроса), при
необходимости задаётся `ZEPHYR_FRONTEND_PROJECT_ID`. Используется настроенная
авторизация скрипта, браузерные Cookie не копируются. Изменять Jenkins не нужно.
После полного успешного основного поиска, включая пустой результат, новый
запрос не выполняется. Полный резервный индекс снимает техническую ошибку
поиска; частичный результат не кэшируется как полный. История запросов остаётся
в логах. Формат комментария не изменён.

Резервный поиск ограничен 8 секундами внутри прежнего общего лимита 45 секунд,
32 страницами, существующими лимитами повторов и Retry-After. Запрашиваются
только id/key/name, размер страницы 5000; фактическое ограничение сервера
учитывается смещением на количество полученных записей. Изменение total,
повтор ключей, неверное смещение и пустая промежуточная страница считаются
неполным поиском. Работоспособность с авторизацией Jenkins требует проверки
следующим запуском: предоставленный пример получен с браузерной авторизацией.

### Отлинкованные задачи: другой установленный релиз

Для отлинкованных Story/Task/Bug проверяется связь с другим релизом независимо
от исключений PR (`review_confirmed`, связь с задачей текущего релиза).
Текущий релиз не учитывается. Кандидаты — связанные задачи из проекта релиза
или с типом Release / Релиз / Релизный объект; учитываются оба направления связи.
Статусы всех кандидатов загружаются одним пакетным запросом.
Хотя бы один другой релиз должен иметь статус «Установлен на ПРОМ».
Если такого релиза нет или статус не удалось подтвердить — блокирующая ошибка.
Подтверждённый установленный релиз разрешает merged PR отлинкованной задачи.
Неполученные задачи и неполная история связей также блокируют готовность.
