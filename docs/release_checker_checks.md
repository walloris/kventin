# Проверки release_checker.py

Документ описывает активные проверки, которые сейчас вызываются из `scripts/release_checker.py`.
Примеры ниже приведены в том же стиле, в котором сообщения попадают в консольный отчет и Jira-комментарий.

## Общий формат отчета

Ошибка:

```text
❌ [HRC-4360] [web][posts][neuro] После удаления поста пост не исчезает из виджета... (Иванов Иван Иванович)
   🔗 https://jira.sberbank.ru/browse/HRC-4360
   🔴 Story: отсутствует описание
```

Предупреждение:

```text
⚠️ [HRC-4360] [web][posts][neuro] После удаления поста пост не исчезает из виджета... (Иванов Иван Иванович)
   🔗 https://jira.sberbank.ru/browse/HRC-4360
   ⚠️  Zephyr: не удалось получить ТК (Read timed out)
```

Jira-комментарий содержит одну таблицу **«Объект релиза — Ошибки»**. Одна строка — одна задача со ссылкой и краткой темой, все её замечания собраны вместе без повторов. Общие ошибки относятся к самому релизу. Красная рамка, фон и текст означают неуспешную проверку; зелёные — успешную. Цвет оформляется wiki-макросами `panel` и `color`, без отдельного вступления и заключения.

В комментарии нет реестра этапов, времён, счётчиков, HTTP-кодов, endpoint, stack trace и диагностических подробностей. Техническая ошибка заменяется коротким сообщением о том, что не удалось проверить; исходная причина сохраняется в консоли и подробном отчёте. Необязательная диагностика GigaChat и Zephyr debug в комментарий не попадает. При успехе без замечаний остаётся строка релиза «Ошибок нет».

```text
|| Объект релиза || Замечания ||
| HRC-4360 — Проверка профиля | Нет описания. \\ Не найден ПР, связанный с задачей. |
```

## 0. Обязательный блокирующий SDD-гейт

SDD реализован непосредственно на Python в `release_checker.py` и
`masked_release_cheker.py`. Node.js, отдельный `.mjs`, дочерние процессы и новые
зависимости не нужны. Используются уже установленный `requests`, URL и токен из
существующей конфигурации Jira. Запуск остаётся прежним:

```text
python release_checker.py https://jira.sberbank.ru/browse/HRPRELEASE-149901
```

Гейт всегда выполняется первым, включая Hotfix и `--dry-run`. Подтверждённое
нарушение (FAIL) или техническая ошибка (INCOMPLETE) блокируют релиз и сразу
останавливают остальные проверки. Диагностические команды не являются проверкой
готовности релиза. По исходной политике неопределённый openspec не блокирует:
он отображается как предупреждение (WARN), остальные проверки продолжаются.

При отказе для каждой Story выводятся конкретные замечания в консольном отчёте
и Jira-комментарии со ссылкой на Story:

- Нет лейбла: добавить в Jira лейбл `SDD` без `#` (регистр не важен).
- Нет совпадения openspec: проверить пути файлов связанных коммитов в Jira dev-status.
  Разрешён путь `openspec/.*<STORY-ID>.*`, включая `openspec/changes/archive/<дата>-<ID>/...`.
  Создавать отдельный каталог `openspec/<STORY-ID>` не требуется.
- Отсутствуют оба требования: выводятся оба замечания.
- Неопределённый openspec: отдельное предупреждение о недоступных данных,
  без утверждения, что артефактов нет.

Ошибки запросов сообщают HTTP-код, таймаут, проблему сети, TLS или формата ответа
без тела ответа, токена и других секретов. Используется та же TLS-политика, что
и у Python-запросов валидатора: `RELEASE_CHECKER_VERIFY_SSL` и
`RELEASE_CHECKER_CA_BUNDLE`. Для запросов задан таймаут подключения 5 секунд,
чтения — 30 секунд, чтобы проверка не зависала без ограничения.

Базовая проверка коммитов Story сохраняет правила JavaScript-гейта с обновлённым поиском openspec:

- До 200 напрямую связанных Story, без пагинации и фильтра по типу связи.
- Сравнение лейбла с `sdd` без учёта регистра, без удаления пробелов или `#`.
- openspec ищется в файлах коммитов dev-status, а не в текущем дереве репозитория;
  путь должен соответствовать `openspec/.*<STORY-ID>.*` без учёта регистра.
  `openspec/` может находиться в любой части пути, а ID — в любой позиции после него:
  например, `docs/openspec/changes/feature-ST-1-new/spec.md` подходит для ST-1.
  Границы ID не проверяются (ST-1 также совпадает с ST-10). ID перед `openspec/`
  сам по себе не подходит. Как и в JavaScript, поиск не пересекает перевод строки.
- Нет Story — успех. Неопределённый openspec исключается из ошибок даже при
  отсутствии SDD у этой Story. Это сохранённая политика исходного гейта.
- Отсутствующий issue ID, нулевой repo count и HTTP-ошибка summary означают
  openspec=false, как в исходнике.
- До четырёх запросов detail с паузой 11 секунд перед каждым; непустой detail
  разбирается даже при ошибке другого инстанса. Пустой detail без ошибок означает
  openspec=false. Четыре неуспешных ответа detail означают unknown.
- Сетевая ошибка или некорректный JSON прекращают гейт с техническим отказом.

Для базовой проверки коммитов проверены одинаковые вердикты Python и исходного JavaScript на 16 наборах ответов
API, включая ошибки, повторные запросы, unknown и префиксное совпадение ID.
Постоянные тесты проверяют Python без Node.js и без обращения к рабочим сервисам.

Диагностика одного конкретного примера без запуска остальных проверок и без записи в Jira:

```text
python release_checker.py --diag-sdd SEARCHCS-1831 HRPRELEASE-147210
```

Последний ключ задаёт контекст релиза и включает поиск в исходниках его PR.
Без него проверяются только коммиты Story, что явно указано в диагностике.
Для проверки конкретной ссылки можно добавить четвёртый параметр:

```text
python release_checker.py --diag-sdd SEARCHCS-1831 HRPRELEASE-147210 https://stash.sigma.sbrf.ru/projects/HRPLATFORM/repos/spine-search/pull-requests/1381
```

Строки `[SDD DATA]` показывают источник, repo count из summary, число групп,
репозиториев, коммитов, файлов, пропущенных массивов, совпадений и до пяти примеров
путей. Они не содержат заголовков авторизации, токенов, тел файлов или сырых ошибок API.
Примеры путей ограничены по длине. В обычном запуске диагностика управляется
`RELEASE_CHECKER_DEBUG_HTTP`; `--diag-sdd` включает её на время своего выполнения.

Отсутствующий массив `files`, отсутствующие `commits`, неполные списки (`fileCount`
больше числа полученных файлов) и неподдерживаемая структура пути — INCOMPLETE,
если положительного совпадения не найдено. Это блокирует релиз и не объявляет,
что артефактов в Bitbucket нет. Видимое дерево Bitbucket и список файлов коммитов
из Jira — разные источники; отсутствие совпадения во втором не доказывает отсутствие
файлов в первом. Для определения конкретной проблемы интеграции нужен `[SDD DATA]`
из рабочей среды.

Если `files` отсутствует, пути имеют неподдерживаемую структуру или `fileCount`
превышает размер превью, валидатор дочитывает изменения **того же связанного коммита**
через Bitbucket `/rest/api/1.0/projects/<project>/repos/<repo>/commits/<id>/changes`.
Адрес и ID берутся из метаданных репозитория/коммита Jira; посторонние репозитории
и текущее дерево другой ветки не сканируются. Обрабатываются страницы `values`
с переходом по `nextPageStart` до `isLastPage=true` и пути `components`, `toString`
или `parent`/`name`. Положительное совпадение завершает поиск досрочно.
Отсутствие совпадения подтверждается только при полном списке файлов, включая
проверку `fileCount`; серверное усечение, сломанная пагинация, предел 100 страниц,
ошибки доступа/сети дают INCOMPLETE и блокируют релиз.

### Исходное дерево релизного PR

Если коммиты Story не подтверждают openspec, обычный запуск автоматически использует
контекст проверяемого релиза. PR релиза берутся из Jira dev-status (`dataType=pullrequest`)
и, если там нет ссылок, из remote links релизной задачи. Поэтому PR должен быть связан
с релизом в Jira. Номер PR, репозиторий и SHA конкретного примера не зашиты в код.

Для найденного PR читаются метаданные Bitbucket. Принимается только исходная ветка
`release/<RELEASE-KEY>`; PR другой релизной ветки и DECLINED пропускаются.
Для одного репозитория/ветки выбирается открытый PR, затем наиболее свежий по
`updatedDate` и ID. Если открытых нет, используется наиболее свежий MERGED.
Так старый PR не подменяет дерево актуального релиза.

Пути читаются рекурсивно через `/repos/<repo>/files?at=<fromRef.latestCommit>` с пагинацией.
Используется **исходный** репозиторий `fromRef.repository` (включая fork), а не целевой
репозиторий PR и не default branch. Один SHA фиксируется на все страницы; содержимое
файлов не загружается. Список путей сохраняется в памяти только на время текущей
проверки релиза и повторно используется для всех связанных Story.

Это проверка наличия артефакта в исходниках релиза: он может уже существовать и не
входить в изменения коммитов, которые Jira связала непосредственно со Story.
Для каждого Story отдельно по-прежнему требуется лейбл SDD. Ошибки доступа и
неполная выдача дерева не превращаются в доказательство отсутствия артефактов.
Диагностика `release_source` показывает репозиторий, ветку и зафиксированный SHA;
`release_artifacts` показывает совпадения по каждой Story.

Контракт: [Bitbucket — метаданные PR](https://developer.atlassian.com/server/bitbucket/rest/v1005/api-group-pull-requests/),
[список файлов в конкретном commit/ref](https://developer.atlassian.com/server/bitbucket/rest/v901/api-group-repository/).

По умолчанию используются существующие настройки `config['bitbucket']['url']`,
`config['bitbucket']['token']` и `config['bitbucket']['verify_ssl']`. Если отдельный
Bitbucket-токен в этой секции пуст, поддерживается прежнее поле
`config['jira']['bitbucket_token']`; обычный Jira-токен не используется.
Токен Bitbucket должен иметь право чтения нужного репозитория (REPO_READ).
Явные `RELEASE_CHECKER_CA_BUNDLE` / `RELEASE_CHECKER_VERIFY_SSL` имеют приоритет
над локальным `bitbucket.verify_ssl`.

`BITBUCKET_BASE_URL` и `BITBUCKET_API_TOKEN` в `.env`/окружении необязательны:
непустые значения переопределяют конфигурацию, пустые сохраняют её. Если адрес
меняется на другой, токен из старой конфигурации туда не переносится автоматически:
требуется явно задать токен для нового адреса.
Bitbucket-токен привязан к настроенному адресу; редиректы не выполняются.
Без токена в конфигурации и окружении возможен только анонимный доступ.
Диагностика `bitbucket_changes` показывает HTTP-код, страницу и режим авторизации,
а `expanded_files` — результат после дочитывания. Секреты в лог не выводятся.
Новых библиотек, Node.js и отдельных файлов по-прежнему не требуется.

Контракт: [Bitbucket Data Center — Get changes in commit](https://developer.atlassian.com/server/bitbucket/rest/v900/api-group-repository/).

Упакованный `masked_release_cheker.py` содержит полный актуальный исходник
`release_checker.py`; совпадение распакованного кода проверяется тестом.

## 1. Релизный тикет

Проверяется, что релизный тикет доступен по ключу.

Успех:

```text
Релизный тикет найден
```

Ошибка:

```text
Критическая ошибка: Не удалось получить тикет релиза: <текст ошибки>
```

## 2. Обязательный лейбл контура

Проверяется у самого релиза, каждой Story и каждого Bug/Defect/Ошибка.
Должен быть хотя бы один лейбл без учета регистра:

- `web`
- `back`
- `mobile`

Успех:

```text
Release: обязательный лейбл контура указан ✓
Story: обязательный лейбл контура указан ✓
Bug: обязательный лейбл контура указан ✓
```

Ошибка:

```text
Release: отсутствует обязательный лейбл контура. Должен быть один из: back/mobile/web
Story: отсутствует обязательный лейбл контура. Должен быть один из: back/mobile/web
Bug: отсутствует обязательный лейбл контура. Должен быть один из: back/mobile/web
```

## 3. Тип релиза Hotfix

Тип определяется по `customfield_23500`.
Если значение равно `Hotfix` без учета регистра, включаются hotfix-правила для багов.
Проверки ТЦ по КЭ для `web`/`back` выполняются только для обычных релизов, не для Hotfix.

Информационный вывод:

```text
🔥 Тип релиза: Hotfix — применяются дополнительные проверки
```

## 4. Сабтаска тестирования

У релиза ищется сабтаска, в названии которой есть `тестирование`.
В найденной сабтаске должно быть списанное время.

Успех:

```text
Затрекано 4.50ч
```

Ошибки:

```text
Сабтаска с 'Тестирование' не найдена
Нет затреканного времени
```

## 5. Артефакты релиза: комментарии тестировщика и списание времени

Для задач из состава релиза по связям `consist of` / `is part of` проверяется:

- есть комментарий от разрешенного тестировщика (включая Лакутина Романа Денисовича);
- у каждого тестировщика, оставившего комментарий, есть списанное время;
- если комментарий оставил Никонов Александр Алексеевич или Метляев Игорь Андреевич, списанное время от него не требуется;
- исключение по списанному времени не применяется для проектной области `HRC`;
- для Story время может быть списано в самой Story или в связанной тестовой Task.

Успех:

```text
Есть комментарии от: Симиник Даниил Григорьевич
У всех тестировщиков с комментариями, для которых требуется worklog, есть списанное время ✓
```

Ошибки:

```text
Нет задач со связью 'consist of' / 'is part of'
Нет комментариев от тестировщика
Нет затреканного времени от тестировщиков с комментариями: Симиник Даниил Григорьевич
Ошибка проверки артефактов: <текст ошибки>
```

## 6. Тестовое покрытие

Для задач состава релиза проверяется наличие прямо связанных ТК из `HRPQA` через Zephyr Scale Server/DC. JQL-функция Xray `hasTestCoverage()` больше не вызывается. Полученные ТК повторно используются для проверки Approved и вида тестирования.

Ошибка:

```text
Отсутствует тестовое покрытие (нет прилинкованных ТК)
```

Техническая ошибка, приводящая к `INCOMPLETE` обязательного этапа:

```text
Zephyr: не удалось проверить покрытие (<текст ошибки>)
Zephyr: не удалось подтвердить прямую связь с ТК: HRPQA-T12345
```

## 7. Zephyr: прилинкованные ТК у Story/Bug

Для задач из состава релиза проверяются прямые прилинкованные ТК в пространстве `HRPQA`.

Основной запрос — `GET /rest/atm/1.0/issuelink/{issueKey}/testcases` **без параметра fields**, как в версии до 08.10.2026. При недоступном endpoint, некорректном ответе или неполной странице используется `GET /rest/atm/1.0/testcase/search` с запросом `projectKey = "HRPQA" AND issueKeys IN ("HRC-4360")`, `startAt` и `maxResults=100`. Полный ответ issuelink по контракту API содержит все связанные ТК; резервный поиск читает все страницы. Проверяются ключи, формат ответа и продвижение пагинации. Неполный список не засчитывается как успешная проверка.

Полные данные из списка используются без дополнительных запросов деталей. Если нужных полей нет, выполняется `GET /rest/atm/1.0/testcase/{key}` без проекции полей. Поддерживается старый текстовый `id` вместо `key` в списках. Если ключ присутствует в ответе деталей, он должен совпадать с запрошенным; его отсутствие допускается при наличии содержательных полей ТК. Ошибки загрузки списков, деталей ТК/ТЦ и технически неуспешного поиска ТЦ не кэшируются как пустые данные. Прямая связь проверяется по полям связей; `HRC-4360` не совпадает с `HRC-43601`.

На поиск списка ТК одной задачи, включая резервный endpoint и все страницы, отводится 45 секунд. Одна серия запросов ограничена 32 секундами и максимумом `ZEPHYR_MAX_RETRIES_PER_REQUEST` попыток (по умолчанию 3), с прежним таймаутом 10 секунд на попытку. Паузы по умолчанию — 0,5 и 1 секунда. `Retry-After` действует и при переходе на резервный endpoint; превышающее бюджет ожидание не выполняется. TLS/401/403 прекращают обращения; прочие неуспешные серии учитываются в общем лимите Zephyr. Эти бюджеты ограничивают запросы и ожидания, но не являются жёстким таймаутом DNS и всего процесса.

Контракт endpoint, параметров `fields` и синтаксиса поиска сверяется с [официальной документацией Zephyr Scale Server/DC](https://support.smartbear.com/zephyr-scale-server/api-docs/v1/).

Проверки:

- все найденные ТК должны быть в статусе `Approved`;
- для `Bug` / `Defect` / `Ошибка` поле `Вид тестирования` должно быть `Регресс`;
- для `Story`, где `customfield_24000` = `Да`, поле `Вид тестирования` должно быть `Новый функционал`;
- для `Story`, где `customfield_24000` = `Нет`, поле `Вид тестирования` должно быть `Регресс`;
- ТК, которые пришли из контекста ТЦ/результата выполнения и не имеют прямой связи с задачей, пропускаются с предупреждением.

Успех:

```text
Zephyr ТК [HRPQA-T12345] в статусе 'Approved' ✓
Zephyr ТК [HRPQA-T12345]: Вид тестирования = 'Регресс' ✓
```

Ошибки:

```text
Zephyr ТК [HRPQA-T12345] «Проверка профиля»: не в статусе 'Approved' (текущий: 'Draft')
Zephyr ТК [HRPQA-T12345] «Проверка профиля»: 'Вид тестирования' = 'Новый функционал', ожидается 'Регресс'
Zephyr: задача есть в Jira, но нет прилинкованных ТК в пространстве HRPQA
```

## 19. Наличие Pull Request — неблокирующая проверка

Для каждой Story/Bug/Defect/Ошибка в составе релиза выполняется поиск Pull Request. Если PR не найден или API недоступен, результат — предупреждение у этой задачи, без блокировки выпуска.

Для Story проверяется только сама Story. PR в Task внутри Story не засчитывается для этой проверки.
Для Bug/Defect/Ошибка проверяется сама задача.

Все обращения к Bitbucket используют общий клиент SDD: настройки адреса, токена
и TLS, чтение полного объекта и всех страниц, проверку адреса и отказ от редиректов.
Jira передаёт связи, а наличие PR и его состояние подтверждаются непосредственно
в Bitbucket. Счётчик Jira сам по себе больше не подтверждает PR.

1. Из Jira `dev-status/1.0/issue/detail` (`stash/pullrequest`) берутся ссылки PR.
   Для проверки наличия PR remote links читаются, если ссылок нет.
   Для проверки MERGED читаются все источники независимо от уже найденного OPEN PR.
2. Каждая ссылка проверяется прямым чтением объекта PR в Bitbucket: ID и состояние
   OPEN/MERGED/DECLINED должны соответствовать реальному объекту.
3. Если ссылок нет либо требуется полный поиск MERGED, читаются связанные с этой задачей коммиты через Bitbucket
   `/rest/jira/1.0/issues/{key}/commits`, затем PR каждого коммита. Состояние PR
   также проверяется отдельным чтением объекта.
4. Если интеграционный маршрут Bitbucket недоступен, используется тот же источник
   ссылок на коммиты, что и в SDD: Jira summary/repository detail версии 1.0.
   Полное сообщение каждого коммита читается напрямую из Bitbucket. Счётчик
   repository в summary означает количество коммитов: два коммита одного
   репозитория не считаются неполным ответом.

Неполные страницы, HTTP-ошибки, отсутствие обязательных полей или исчерпание
бюджета означают «не удалось проверить», а не подтверждённое отсутствие PR.
Положительное доказательство сохраняет силу при недоступности другого источника.
Успешные данные кэшируются на запуск релиза; кэш и состояние ограничений сервера
сбрасываются перед следующим релизом. Общий Retry-After предотвращает новые
обращения к ограниченному серверу, без долгих пауз и перебора псевдонимов API.
Сохраняются бюджеты 30 секунд на задачу и 120 секунд на этап; socket timeout
ограничивается оставшимся бюджетом. Это не жёсткий таймер DNS/сетевого стека.

Тот же клиент используется для merged PR, GigaCode, `--diag-pr`,
`--diag-gigacode` и PR-части `--diag-lookups`. Диагностика только читает данные;
обычный `--dry-run` не меняет AIFIXED и не публикует комментарий.

Контракты: [Bitbucket Jira integration](https://docs.atlassian.com/bitbucket-server/rest/7.9.0/bitbucket-jira-rest.html),
[Bitbucket Pull requests](https://developer.atlassian.com/server/bitbucket/rest/v1005/api-group-pull-requests/).

Успех:

```text
Pull Request найден в HRC-4360 (Bitbucket: подтверждён связанный PR) ✓
```

Ошибка:

```text

```

Предупреждение:

```text

```

## 21. Отлинкованные от релиза задачи, PR и статус

По changelog релиза определяются задачи, которые удалены из его связей и сейчас
не входят в состав. Для Story/Task/Bug/Defect/Ошибка читаются связанные PR
напрямую из Bitbucket общим клиентом SDD и статус самой задачи из Jira.

- PR подтверждённо нет: отлинковка допустима; статус задачи, наличие другого
  релиза и его статус не ограничивают результат.
- Есть любой PR (OPEN, MERGED или DECLINED): статус задачи Cancelled/Canceled
  или Rejected — блокирующая ошибка. Лейбл review_confirmed и связь с задачей
  текущего релиза не отменяют это правило.
- Есть PR, но нет MERGED: требуется связь с другим релизом; статус того релиза
  не ограничивается. Если из связи не известен тип объекта, он подтверждается
  пакетным чтением Jira; обычная Story из проекта релизов не засчитывается.
- Есть хотя бы один MERGED PR: требуется другой связанный релиз в статусе
  «Установлен на ПРОМ». Одна такая связь достаточна. Текущий релиз не учитывается.
- PR не удалось проверить или список неполон: выводится предупреждение;
  недоступность данных не считается подтверждённым отсутствием PR.

Отсутствие связи с требуемым другим релизом блокирует готовность. При MERGED
неполученный статус другого релиза также не подтверждает выполнение условия.
Неполученная задача или неполная история связей сохраняют блокирующий результат.

## 29. Контроль полноты и диагностика джобы

Каждый запуск формирует реестр из 16 этапов. Для каждого в консоли немедленно печатаются START, итоговый статус, время, число объектов и количество успешных результатов, ошибок и предупреждений. Строки выводятся без буферизации. Этот диагностический реестр остаётся в логе; в Jira публикуется краткая цветная таблица объектов и замечаний, описанная в начале документа. Текст из задач экранируется, включая разделители таблицы, wiki-макросы и переносы строк в HTML-энтити.

- PASS — есть успешные результаты, нет ошибок/предупреждений.
- FAIL — найдены нарушения правил.
- INCOMPLETE — нет необходимых данных либо этап завершился технической ошибкой. Для обязательного этапа это блокирующая ошибка; неполученный PR, GigaCode и GigaChat сохраняют рекомендательный статус. Подтверждённый merged PR у исключённой задачи остаётся блокирующим нарушением.
- WARN — этап дал предупреждения.
- SKIP — этап неприменим по явному условию (например, нет web/back либо релиз Hotfix); причина указана.
- NO_FINDINGS — этап завершился без зарегистрированных результатов. Это не утверждение, что объекты были проверены: применимых объектов может не быть.

Необработанная ошибка одного этапа не прерывает последующие этапы. Обязательные проверки, которым не удалось получить данные, не маскируются под успех. Все Jira-поиски получают полные страницы результатов (`maxResults=False`); одинаковые успешные чтения задач, комментариев, worklog, полей и поисков кэшируются в пределах запуска. Запись и ошибочные SDK-запросы не кэшируются. Новый запуск очищает оперативные кэши.

В логе #1452 от 08.10.2026 Zephyr не выполнил проверки ТК/ТЦ из-за повторных `CERTIFICATE_VERIFY_FAILED`: 20 неуспешных запросов, каждый с ретраями. После ошибки поиска запускался ещё и перебор номеров ТЦ. Комментарий скрывал эти предупреждения. Исправления: явная единая настройка TLS для Jira/Zephyr, отсутствие ретраев при ошибке сертификата/401/403, прекращение резервного сканирования при TLS/401/403 или исчерпании лимита ошибок, видимые INCOMPLETE и предупреждения в комментарии. Причина недоступности PR теперь выводится отдельно: TLS, timeout, HTTP-код, ошибка JSON/API; по старому логу установить её однозначно нельзя.

В логе #1455 обнаружены таймаут покрытия через Xray, таймаут metadata полей Jira с повторным использованием пустого кэша и HTTP 429 при проверке PR. При этом сами ТК были получены (35 кейсов), проверка наличия ПР прошла для 9 задач, а проверка ТЦ останавливалась на metadata КЭ. Текущий код читает metadata с тремя ограниченными попытками (до 15 секунд на запрос, 35 секунд на серию), неудачный результат не сохраняется в кэш полей или сервисов. Таймаут чтения Jira SDK увеличен с добавленных сегодня 10 до 30 секунд. Для ТК внутри ТЦ сообщение «все Approved» выводится только при успешной проверке каждого ТК. Несоответствия вида тестирования остаются ошибками качества данных и требуют исправления в Zephyr.

Сравнение с последней версией до сегодняшних изменений (`8a758d6`): в `f38c5e1` удалили прямое чтение ПР без summary и свойства Jira, сократили таймаут деталей с 30 до 3 секунд и ввели кэш неуспеха на весь запуск. В `5ed6b5f` добавили проекцию полей Zephyr, отвергли текстовый `id` ТК и ответы деталей без `key`, ограничили серию Zephyr 12 секундами вместо прежних трёх попыток по 10 секунд. Восстановлены прежние совместимые запросы и резервные источники; ограничения общего времени, строгая проверка свидетельств ПР и различение ошибок API/отсутствия данных сохранены. Совместимость проверяется синтетическими ответами, включая локальный HTTP-сервер с задержкой детали ПР 3,2 секунды. Без актуального лога после `5ed6b5f` нельзя приписать конкретный сбой рабочего сервера одной из этих причин.

TLS-настройки:

- `RELEASE_CHECKER_CA_BUNDLE=/path/to/corporate-ca.pem` — использовать корпоративный CA bundle;
- `RELEASE_CHECKER_VERIFY_SSL=1` — включить проверку стандартным хранилищем доверия;
- без этих переменных сохраняется прежняя политика скрипта `verify=False`, теперь передаваемая явно, чтобы `REQUESTS_CA_BUNDLE` не меняла её неявно. Автоматического отключения TLS-проверки после ошибки нет.

Для диагностики каждого HTTP-запроса включить `RELEASE_CHECKER_DEBUG_HTTP=1`. Лог содержит путь endpoint, безопасные параметры идентификации Jira, номер попытки, результат и длительность; заголовки авторизации и тела ответов не выводятся. Медленные и неуспешные запросы логируются и без этой переменной.

Пример запуска в окружении джобы без записи комментариев и лейблов:

```bash
RELEASE_CHECKER_DEBUG_HTTP=1 python -u scripts/release_checker.py --dry-run HRPRELEASE-146076
```

`--dry-run` выполняет чтение и проверки, выводит требуемые изменения AIFIXED, но не применяет их. Код выхода 1 сохраняется при нарушениях обязательных проверок. Этот режим использует реальные сервисы; локальные тесты работают на синтетических ответах и не публикуют данные в Jira.


## 30. Уточнения от 12.10.2026: комментарий, ТЦ и неблокирующий PR

Комментарий — одна таблица «Объект релиза → Замечания» в цветной Jira panel. Строки содержат ссылки на задачи и только их замечания. GENERAL объединяется со строкой релиза. Зелёная — при отсутствии замечаний либо только при ненайденных/непроверенных PR; эти замечания всё равно видны у соответствующих задач. Остальные ошибки качества не смягчаются.

## 31. Уточнения от 15.10.2026: поиск ТЦ и комментарий

Поиск ТЦ использует документированный `GET /rest/atm/1.0/testrun/search` с фильтром `projectKey` и лёгкой проекцией `key,name,issueKey,issueLinks`. Фильтры `name` и `issueKey` в этом endpoint не поддерживаются серверным API и давали ошибку `400`; они больше не применяются в обычном запуске. Результат читается страницами по 200 элементов (можно изменить `ZEPHYR_CYCLE_INDEX_PAGE_SIZE`) с общим лимитом в 45 секунд. Частичный список не кэшируется как полный и фиксируется отдельным кратким замечанием без HTTP-диагностики в Jira.

Прямой запасной поиск сначала проверяет уже известное окно номеров ТЦ, затем обновляет его границу. Поэтому медленные новые номера не вытесняют проверку старта окна. Локальный кэш теперь по умолчанию размещается во временной директории пользователя; невозможность его сохранить выводится только в консоль и не считается замечанием к релизу.

Jira-комментарий выводит светлую таблицу с цветным заголовком результата: зелёным при отсутствии замечаний, красным при замечаниях. В каждой строке замечания пронумерованы, технические детали и повторяющиеся сообщения о не связанных ТК скрыты. Отсутствие багов в составе релиза — успешный результат. В список допустимых закрывающих sub-task «Анализ архитектуры» добавлена Плохотнюк Анна Дмитриевна.

## 32. Диагностика PR/ТЦ и комментарий от 18.10.2026

Изменения не увеличивают существующие сетевые бюджеты:

- PR: 30 секунд на задачу, 120 секунд на этап. Внутри 5 секунд поиска summary одна попытка теперь может ждать до 5 секунд вместо 3. Это позволяет получить медленный успешный ответ, не расходуя время на повтор. В detail оставшееся время делится между запрошенными типами данных: зависший `pullrequest` больше не вытесняет `repository`/`commit`. В проверке наличия PR общий бюджет detail остаётся 16 секунд. Не начатые из-за исчерпания бюджета запросы не попадают в кэш ошибок и не отключают источник для следующих задач.
- ТЦ: общий бюджет поиска остаётся 45 секунд. На issuelink и индекс проекта вместе отводится максимум 25 секунд, на Jira metadata — максимум 8 секунд; оставшееся время доступно прямому поиску/кэшу. Неиспользованное время остаётся в общем бюджете. Быстрые временные ошибки issuelink допускают повтор в пределах прежних 10 секунд, вместо немедленного перехода к широкому поиску. Значения приведены для настроек по умолчанию.
- Не более трёх попыток PR и `ZEPHYR_MAX_RETRIES_PER_REQUEST` попыток Zephyr (по умолчанию 3). Паузы, `Retry-After` и все резервные источники учитывают общий дедлайн. TLS и ошибки прав не повторяются. Существующие ограничения количества страниц, сканирования и неуспешных запросов сохранены.

Это лимиты сетевых ожиданий и запуска следующих запросов, а не жёсткий таймер процесса: DNS, загрузка тела ответа, Jira SDK, прочие проверки и запись логов могут занимать дополнительное время. Не доказано, что реальный запуск стал быстрее или что рабочий сервер перестал отдавать таймауты; это проверяется по следующему запуску. Реальные API при локальной проверке не вызывались.

### Запуск для разбора

**Промежуточная версия для Jenkins:** подробная диагностика включена по умолчанию параметром `HTTP_DEBUG_ENABLED = True` в начале `scripts/release_checker.py`. Запускайте существующую джобу как обычно, без изменения Jenkins-скрипта. События `[HTTP DEBUG]` и итоги проверок появятся в Console Output; для анализа достаточно прислать этот вывод. Обычная публикация комментария и обновление AIFIXED сохраняются, если команда не содержит `--dry-run`.

Чтобы выключить подробную диагностику, установите `HTTP_DEBUG_ENABLED = False`. При необходимости переменная окружения `RELEASE_CHECKER_DEBUG_HTTP=0` или `1` переопределяет параметр в коде. Явное выключение отключает подробные события и в консоли, и в JSONL-файле; обычные сообщения об ошибках и результатах остаются. Строка `[DIAGNOSTICS] HTTP=ON/OFF` в начале запуска показывает выбранный режим. Если задан `RELEASE_CHECKER_HTTP_LOG`, включённая HTTP-диагностика записывается в этот файл вместо консоли.

Для отдельного локального запуска с сохранением файлов:

В окружении с обычной конфигурацией Jira и зависимостями выполните команду ниже, заменив `HRPRELEASE-123456` нужным ключом. Запускайте из корня репозитория; интерпретатор можно заменить на используемый в джобе.

```bash
RELEASE_CHECKER_HTTP_LOG=release-http.jsonl \
RELEASE_CHECKER_COMMENT_PREVIEW=release-comment.wiki \
python scripts/release_checker.py --dry-run HRPRELEASE-123456
```

Пришлите `release-http.jsonl` и, для оценки комментария, `release-comment.wiki`. В режиме `--dry-run` комментарий не публикуется, старые комментарии не удаляются, AIFIXED не проставляется. Локальный кэш ТЦ по-прежнему может обновляться. Код выхода 1 означает, что найдены замечания, блокирующие релиз; это само по себе не означает падение скрипта.

JSONL содержит время UTC, источник, путь без query string, разрешённые параметры, идентификатор запроса, номер попытки, выделенный таймаут, остаток бюджета, HTTP-статус, длительность, размер тела, тип содержимого, причину повтора и длительность паузы. Для JSON сохраняется ограниченная структура известных полей и размеры коллекций, без значений названий, описаний, токенов, cookies, заголовков авторизации и сырых тел. В лог попадают также чтения кэша PR, отключение источника после ошибок, итог поиска ТЦ и итоги этапов. Если JSON не разобран, остаются HTTP-статус, тип содержимого и тип исключения. Jira SDK и старые отдельные `--diag-*` не являются частью этого HTTP-трейсинга; старые диагностические режимы могут печатать сырые данные, поэтому для первого разбора используйте команду выше.

Файл JSONL дополняется при повторном запуске. Без `RELEASE_CHECKER_HTTP_LOG` подробные события выводятся в консоль при включённом `HTTP_DEBUG_ENABLED` или `RELEASE_CHECKER_DEBUG_HTTP=1`. `RELEASE_CHECKER_COMMENT_PREVIEW` сохраняет текст только в `--dry-run`.

### Диагностическая версия после №1562

Превышение норматива времени Story в тестовых статусах теперь является предупреждением «Отклонение»: видно в комментарии и подробной таблице, не увеличивает число блокирующих ошибок. Само по себе отклонение допускает зелёный результат; остальные правила готовности сохранены.

**В этой промежуточной версии включён `LOOKUP_DIAGNOSTICS_ENABLED = True`.** Прежняя команда Jenkins с ключом релиза выполняет только read-only диагностику API, вместо обычной проверки готовности. Комментарии не создаются и не удаляются, AIFIXED не изменяется. Код 0 означает завершение эксперимента, а не готовность релиза. Для возврата обычной проверки: `LOOKUP_DIAGNOSTICS_ENABLED = False` в файле либо `RELEASE_CHECKER_LOOKUP_DIAGNOSTICS=0` в окружении. HTTP-логирование — отдельный переключатель; результаты матрицы печатаются независимо от него.

Для явного запуска: `python scripts/release_checker.py --diag-lookups HRPRELEASE-147929`.

Матрица сравнивает:

- PR: единый результат `PR Bitbucket verified`, полученный тем же клиентом, что и обычная проверка; ссылки Jira не заменяют подтверждение в Bitbucket.
- ТЦ: поля и remote links релиза, прямое чтение известного ключа, issuelink `testruns`/`testcycles`, первая страница индекса проекта, запрос имени, параметры `issueKey`/`issueKeys`, отрицательный контроль с `HRPRELEASE-0`, альтернативный `testcycle/search`.

Экспериментальные варианты не предполагаются рабочими заранее. HTTP 200 не считается доказательством: для PR проверяются признаки PR; для ТЦ выводятся число совпадений с релизом, число посторонних элементов и отпечаток ключей страницы. Совпадение отпечатков запроса и отрицательного контроля помогает обнаружить игнорирование фильтра. Найденные циклы не означают, что получен полный список.

Параметры в начале файла:

- `LOOKUP_DIAGNOSTIC_FOCUS = 'both'`: оба семейства; `pr`/`cycles` позволяет исследовать их отдельными запусками. Переопределение: `RELEASE_CHECKER_DIAG_FOCUS`.
- `LOOKUP_DIAGNOSTIC_CYCLE = 'HRPQA-C138867'`: известный ключ из №1562 для проверки прямого чтения. Для другого релиза задайте соответствующий ключ или пустую строку для поиска ключа в метаданных Jira. Переопределение: `RELEASE_CHECKER_DIAG_CYCLE`.
- `RELEASE_CHECKER_DIAG_ISSUE`: необязательный ключ конкретной Story/Bug. Без него выбирается первая задача из связей состава релиза; выбранный ключ печатается в итогах.

Общий бюджет сетевых ожиданий — 130 секунд: до 10 на начальные связи и до 60 на каждое семейство; один диагностический запрос Jira/Zephyr — до 12 секунд, без ретраев и пагинации. PR-часть использует штатное постраничное чтение Bitbucket в своём бюджете. Это не жёсткий таймер процесса: DNS/передача тела могут влиять на фактическую длительность. При исчерпании бюджета оставшиеся варианты явно помечаются SKIP. `Retry-After` общий для всех маршрутов того же сервера; обходить ограничение альтернативными маршрутами эксперимент не пытается. После 429 без заголовка также действует короткая пауза. Поэтому для сравнения всех вариантов может потребоваться отдельный запуск выбранного семейства после снятия ограничения.

Пришлите полный лог следующего запуска, особенно строки `[LOOKUP MATRIX]` и `[LOOKUP MATRIX SUMMARY]`. В них нет сырых тел ответа: только структура, технические статусы, категории ошибок, количества и ключи совпавших циклов. Локальные тесты используют имитацию ответов; доступность маршрутов в корпоративной сети должен подтвердить Jenkins.

Смещение увеличивается на фактическое число элементов, поэтому ограничение размера страницы сервером не приводит к пропускам. Короткая страница не считается концом списка: полнота отмечается только после пустой следующей страницы. Повтор или пересечение ключей страниц, ошибка, 429, лимит страниц или времени оставляют `complete=false`. Найденные к этому моменту ключи сохраняются в итогах. До 32 обрабатываемых страниц, не более 34 вызовов чтения страниц с учётом сравнительных запросов; до 45 секунд в пределах прежнего 60-секундного бюджета семейства ТЦ.

Итог печатается в `[LOOKUP INDEX SUMMARY]`: полнота, причина остановки, число прочитанных страниц и уникальных циклов, найденные ключи нужного релиза. Режим остаётся диагностическим, без публикации комментария и оценки готовности. Полный индекс в файл не записывается: сначала измеряем возможность его получения за допустимое время.

### №1570: подтверждённый способ поиска перенесён в обычную проверку

Для HRPRELEASE-147712 сервер отдал полный компактный индекс: 23059 уникальных циклов, 8 совпадений с релизом. Размер страницы 5000 поддерживается. Пустая страница после смещения 23059 подтвердила завершение обхода; повторов страниц и HTTP 429 не было. Диагностика целиком заняла 26,3 с, включая начальные запросы Jira и сравнительную страницу на 1000 элементов.

В обычной проверке размер `ZEPHYR_CYCLE_INDEX_PAGE_SIZE` по умолчанию теперь 5000 вместо 200. Сравнительный запрос на 1000 элементов не выполняется: для объёма из лога нужны 6 запросов индекса, включая пустую завершающую страницу. Сумма длительностей этих шести запросов из лога — 22,595 с. Бюджеты не изменены: 25 с на основное обнаружение циклов внутри общего 45-секундного бюджета поиска. Короткая страница не признаётся последней автоматически; проверки полноты, повторов, неполного ответа и серверной пагинации сохранены.

`LOOKUP_DIAGNOSTICS_ENABLED = False`: прежняя команда Jenkins снова выполняет обычную проверку, включая публикацию комментария. Если в джобе был задан `RELEASE_CHECKER_LOOKUP_DIAGNOSTICS=1`, его нужно убрать или заменить на 0. Если задан `ZEPHYR_CYCLE_INDEX_PAGE_SIZE`, он переопределяет новый размер по умолчанию. HTTP-диагностика остаётся включённой для следующего контрольного запуска.

Найденные ключи: HRPQA-C138606, HRPQA-C138607, HRPQA-C138608, HRPQA-C138613, HRPQA-C138614, HRPQA-C138615, HRPQA-C138616, HRPQA-C138617. Это подтверждение поиска циклов; чтение деталей всех ТК, проверки PR/GigaCode и итоговая готовность релиза требуют обычного запуска. Не гарантируется такая же длительность при иной нагрузке сервера; при превышении бюджета результат останется неполным.

### Маски ТЦ и соответствие КЭ (21.10.2026)

Для регрессионных web-циклов `WEB` принимается как вариант канала `SberBrowser`, в том числе для NEUROUI. Остальные поддерживаемые каналы и правила обязательности сохраняются. Имена вида `HRPRELEASE-148167. HRP.CoreUI-Dates(3304476). WEB. Regress` принимаются с пробелами вокруг точек, числовым ID в скобках, русским `Регресс` и английскими `Regress`/`Regression`. Для сопоставления имени КЭ с названием ТЦ также допускается значение Jira с префиксом `CI…`: например, `CI01234567 HRP.CoreUI-Dates`. Ключ релиза и само имя сервиса по-прежнему должны совпадать.

Добавлен независимый обязательный этап «Совпадение КЭ задач и релиза». Каждая КЭ каждой задачи состава релиза (`consists of`/`is part of`) должна присутствовать среди КЭ релиза; дополнительная КЭ релиза не является ошибкой. Несовпадение или пустое поле КЭ — блокирующая ошибка. Недоступные данные помечаются как незавершённая проверка. После ошибки одной задачи обрабатываются остальные задачи и последующие этапы. Задачи читаются одним пакетным запросом, без отдельного запроса на каждую КЭ.

При сравнении КЭ учитываются регистр и пробелы вокруг точек. Если обе стороны содержат CI-код, сравниваются коды. Если числовые ID в скобках присутствуют с обеих сторон и отличаются, значения не совпадают. В остальных случаях сравниваются имена без префикса CI и числового ID. Один номер в скобках без совпадения имён недостаточен: `HRP.CoreUI-Dates(3304476)` и `HRP.CoreUI-Posts(3304476)` не считаются одной КЭ.

Исключение относится только к новой проверке совпадения КЭ: релизы с лейблом `mobile` либо одной из КЭ `CI02257858 HRP-ios`, `CI02935717 HRP-Android`, `CI03521872 HRP.iOS МП.МП-iPAD`, `CI06355438 HRP. SberTab`. Распознаются и эти названия без CI-кода. Остальные проверки релиза продолжают выполняться.

### Единый источник GigaCode / AIFIXED

`_lookup_gigacode` использует общий клиент Bitbucket из SDD и возвращает
FOUND / NOT_FOUND / UNKNOWN. Название и описание PR читаются из полного
объекта, сообщения коммитов — из постраничных списков PR и связанных коммитов
самой задачи. Если интеграционный маршрут недоступен, используются ссылки
Jira с последующим чтением полных объектов коммитов в Bitbucket.

- FOUND: поддерживаемый маркер найден в проверенном PR/коммите. Ошибка другого
  источника не отменяет доказательство; найденный результат переиспользуется.
- NOT_FOUND: все необходимые списки и текстовые поля прочитаны полностью,
  маркера нет. Одних счётчиков Jira для этого недостаточно.
- UNKNOWN: источник недоступен, ответ неполон, нет текстовых полей или истёк
  бюджет. Такой результат не кэшируется как отсутствие маркера.

Для общего релизного PR коммит другой Story не подтверждает GigaCode у текущей:
проверяется точное вхождение ключа задачи в ветке PR или сообщении коммита.
Непривязанный маркер в общем PR даёт UNKNOWN. Ранний выход по маркеру одной
Story не сохраняет частичный список коммитов как полный для другой Story.
В названии и описании непосредственно связанного PR сохраняется прежнее правило
распознавания маркеров. Маркеры в служебных метаданных и ошибках не учитываются.

Сохраняются поддерживаемые маркеры, проверка дочерних Task для AIFIXED,
неблокирующие предупреждения при недоступности источника и режим dry-run.
Если одна Task недоступна, а другая подтверждает GigaCode, положительное
доказательство достаточно. Содержимое PR/коммитов, сырые ответы и токены
в диагностике не печатаются; выводятся технические статусы, количества,
причины неполноты и итог проверки.

### Резервный поиск ТЦ через API фронта Zephyr

При неполном или технически неуспешном основном поиске используется
`GET /rest/tests/1.0/testrun/search`, по контракту из браузерного запроса:
`results`, `total`, `startAt`. Поиск охватывает проект целиком без фильтра
выбранной в браузере папки; ключ релиза сопоставляется с названием ТЦ с
проверкой границ (`REL-1` не совпадает с `REL-10`). Связи с Jira в этом
ответе отсутствуют: этот путь предназначен для ТЦ с ключом релиза в имени.
Детали и проверки найденных ТЦ остаются в существующем процессе.

Проект по умолчанию — `88701` (HRPQA из предоставленного запроса), при
необходимости задаётся `ZEPHYR_FRONTEND_PROJECT_ID`. Используется настроенная
авторизация скрипта, браузерные Cookie не копируются. Изменять Jenkins не нужно.
После полного успешного основного поиска, включая пустой результат, новый
запрос не выполняется. Полный резервный индекс снимает техническую ошибку
поиска; частичный результат не кэшируется как полный. История запросов остаётся
в логах. Формат комментария не изменён.

Резервный поиск ограничен 8 секундами внутри прежнего общего лимита 45 секунд,
32 страницами, существующими лимитами повторов и Retry-After. Запрашиваются
только id/key/name, размер страницы 5000; фактическое ограничение сервера
учитывается смещением на количество полученных записей. Изменение total,
повтор ключей, неверное смещение и пустая промежуточная страница считаются
неполным поиском. Работоспособность с авторизацией Jenkins требует проверки
следующим запуском: предоставленный пример получен с браузерной авторизацией.

### Отлинкованные задачи: условия другого релиза

Связь с другим релизом проверяется только после подтверждения наличия PR.
Для OPEN/DECLINED достаточно связи с подтверждённым релизным объектом; «Установлен на ПРОМ» требуется
только при наличии MERGED. Статус самой задачи Cancelled/Rejected при любом
PR запрещён. Без PR отлинковка допустима без дальнейших проверок.
Кандидаты другого релиза определяются по проекту релизного объекта или типу
Release / Релиз / Релизный объект, в обоих направлениях связи.
Статусы нужных релизов читаются пакетно. Проверка не изменяет задачи Jira.

## Уточнения по обязательным проверкам и итоговому результату

Тест-цикл без ключа не позволяет проверить Approved и вид тестирования. Такой
результат — блокирующая техническая ошибка, а не обычное предупреждение.

Итоговый отчёт учитывает и возвращаемое значение `check_release()`, и накопленные
ошибки. Отрицательный результат проверки не может превратиться в сообщение о
готовности только потому, что список ошибок оказался пустым.


## Исправления по ревью комитета

- SDD читает все страницы связанных Story до проверки лейблов и openspec.
  Проверяются total, смещение, повтор задач и изменение списка; неполный поиск
  блокирует дальнейшие этапы. Правила проверки каждой Story сохранены.
- Поиск MERGED объединяет dev-status, remote links и PR связанных коммитов.
  Наличие OPEN PR не подтверждает отсутствие других MERGED PR. Неуспешный
  источник не превращается в доказанное отсутствие MERGED.
- Другой релиз подтверждается по типу Release / Релиз / Релизный объект.
  Совпадение проекта используется только для поиска кандидатов.
- Связанные тест-циклы читаются постранично в прежнем бюджете. Неполный список
  запускает существующий резервный поиск и не кэшируется как полный.
- AIFIXED добавляется отдельной операцией Jira update.labels.add; список меток
  целиком не заменяется. Метки, добавленные пользователем во время проверки,
  сохраняются. Режим dry-run по-прежнему не изменяет Jira.
