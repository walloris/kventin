# Проверки release_checker.py

Документ описывает активные проверки, которые сейчас вызываются из `scripts/release_checker.py`.
Примеры ниже приведены в том же стиле, в котором сообщения попадают в консольный отчет и Jira-комментарий.

## Общий формат отчета

Ошибка:

```text
❌ [HRC-4360] [web][posts][neuro] После удаления поста пост не исчезает из виджета... (Иванов Иван Иванович)
   🔗 https://jira.sberbank.ru/browse/HRC-4360
   🔴 Story: отсутствует описание
```

Предупреждение:

```text
⚠️ [HRC-4360] [web][posts][neuro] После удаления поста пост не исчезает из виджета... (Иванов Иван Иванович)
   🔗 https://jira.sberbank.ru/browse/HRC-4360
   ⚠️  Zephyr: не удалось получить ТК (Read timed out)
```

Успех в итоговый Jira-комментарий обычно не попадает, но пишется во внутренние данные отчета:

```text
✅ Story: описание заполнено ✓
```

## 1. Релизный тикет

Проверяется, что релизный тикет доступен по ключу.

Успех:

```text
Релизный тикет найден
```

Ошибка:

```text
Критическая ошибка: Не удалось получить тикет релиза: <текст ошибки>
```

## 2. Обязательный лейбл контура

Проверяется у самого релиза, каждой Story и каждого Bug/Defect/Ошибка.
Должен быть хотя бы один лейбл без учета регистра:

- `web`
- `back`
- `mobile`

Успех:

```text
Release: обязательный лейбл контура указан ✓
Story: обязательный лейбл контура указан ✓
Bug: обязательный лейбл контура указан ✓
```

Ошибка:

```text
Release: отсутствует обязательный лейбл контура. Должен быть один из: back/mobile/web
Story: отсутствует обязательный лейбл контура. Должен быть один из: back/mobile/web
Bug: отсутствует обязательный лейбл контура. Должен быть один из: back/mobile/web
```

## 3. Тип релиза Hotfix

Тип определяется по `customfield_23500`.
Если значение равно `Hotfix` без учета регистра, включаются hotfix-правила для багов.
Проверки ТЦ по КЭ для `web`/`back` выполняются только для обычных релизов, не для Hotfix.

Информационный вывод:

```text
🔥 Тип релиза: Hotfix — применяются дополнительные проверки
```

## 4. Сабтаска тестирования

У релиза ищется сабтаска, в названии которой есть `тестирование`.
В найденной сабтаске должно быть списанное время.

Успех:

```text
Затрекано 4.50ч
```

Ошибки:

```text
Сабтаска с 'Тестирование' не найдена
Нет затреканного времени
```

## 5. Артефакты релиза: комментарии тестировщика и списание времени

Для задач из состава релиза по связям `consist of` / `is part of` проверяется:

- есть комментарий от разрешенного тестировщика;
- у каждого тестировщика, оставившего комментарий, есть списанное время;
- если комментарий оставил Никонов Александр Алексеевич, списанное время от него не требуется;
- для Story время может быть списано в самой Story или в связанной тестовой Task.

Успех:

```text
Есть комментарии от: Симиник Даниил Григорьевич
У всех тестировщиков с комментариями, для которых требуется worklog, есть списанное время ✓
```

Ошибки:

```text
Нет задач со связью 'consist of' / 'is part of'
Нет комментариев от тестировщика
Нет затреканного времени от тестировщиков с комментариями: Симиник Даниил Григорьевич
Ошибка проверки артефактов: <текст ошибки>
```

## 6. Тестовое покрытие

Для задач состава релиза проверяется наличие тестового покрытия через JQL `issue in hasTestCoverage()`.

Ошибка:

```text
Отсутствует тестовое покрытие (нет прилинкованных ТК)
```

Предупреждение:

```text
Не удалось проверить покрытие (плагин Xray?): <текст ошибки>
```

## 7. Zephyr: прилинкованные ТК у Story/Bug

Для задач из состава релиза проверяются прямые прилинкованные ТК в пространстве `HRPQA`.

Проверки:

- все найденные ТК должны быть в статусе `Approved`;
- для `Bug` / `Defect` / `Ошибка` поле `Вид тестирования` должно быть `Регресс`;
- для `Story`, где `customfield_24000` = `Да`, поле `Вид тестирования` должно быть `Новый функционал`;
- для `Story`, где `customfield_24000` = `Нет`, поле `Вид тестирования` должно быть `Регресс`;
- ТК, которые пришли из контекста ТЦ/результата выполнения и не имеют прямой связи с задачей, пропускаются с предупреждением.

Успех:

```text
Zephyr ТК [HRPQA-T12345] в статусе 'Approved' ✓
Zephyr ТК [HRPQA-T12345]: Вид тестирования = 'Регресс' ✓
```

Ошибки:

```text
Zephyr ТК [HRPQA-T12345] «Проверка профиля»: не в статусе 'Approved' (текущий: 'Draft')
Zephyr ТК [HRPQA-T12345] «Проверка профиля»: 'Вид тестирования' = 'Новый функционал', ожидается 'Регресс'
```

Предупреждения:

```text
Zephyr: нет задач со связью 'consist of' — проверка ТК пропущена
Zephyr: лимит неуспешных запросов исчерпан, дальнейшая проверка ТК пропущена
Zephyr: не удалось получить ТК (<текст ошибки>)
Zephyr: задача есть в Jira, но нет прилинкованных ТК в пространстве HRPQA
Zephyr ТК [HRPQA-T12345] «Проверка профиля»: не удалось получить детали ТК, статус проверяется по короткому ответу issuelink
Zephyr ТК [HRPQA-T12345] «Проверка профиля» пропущен: в данных ТК нет прямой связи с задачей HRC-4360; вероятно, ТК пришел из ТЦ/результата выполнения
Zephyr ТК [HRPQA-T12345]: поле 'Вид тестирования' не найдено в кастомных полях ТК
Zephyr ТК [HRPQA-T12345]: не удалось получить детали ТК для проверки поля 'Вид тестирования'
```

## 8. Back release: обязательные ТЦ по КЭ

Проверка выполняется только для обычного релиза, не Hotfix, если у релиза есть лейбл `back`.

Для каждой КЭ сервиса из Story/Bug состава релиза должны быть ТЦ:

- `{ключ релиза}.{КЭ сервиса}.ipad/pwa/safari/sberbrowser.Регресс`;
- `{ключ релиза}.{КЭ сервиса}.api.Регресс`;
- если внутри КЭ есть Story с `Новая функциональность = Да`, дополнительно `{ключ релиза}.{КЭ сервиса}.api.НФ`.

Название ТЦ матчится мягко: без учета регистра, лишних пробелов, ID КЭ в скобках, русских/английских алиасов `Регресс`/`Regress`/`Regression`, `НФ`/`NF`, а также допускается дата в конце названия.

Успех:

```text
Back release: для КЭ 'CoreTech(7993288)' найден iPad/PWA/Safari/SberBrowser Регресс ТЦ [HRPQA-C133028] 'HRPRELEASE-131571.CoreTech(7993288).ipad/pwa/safari/sberbrowser.Регресс' ✓
Back release: для КЭ 'CoreTech(7993288)' найден API Регресс ТЦ [HRPQA-C133029] 'HRPRELEASE-131571.CoreTech(7993288).api.Регресс' ✓
Back release: для КЭ 'CoreTech(7993288)' найден API НФ ТЦ [HRPQA-C133030] 'HRPRELEASE-131571.CoreTech(7993288).api.НФ' ✓
```

Ошибки:

```text
Back release: не удалось определить Jira field id для поля КЭ/КЭ сервиса
Back release: ошибка получения задач состава релиза для проверки КЭ: <текст ошибки>
Back release: не заполнено поле КЭ сервиса (customfield_xxxxx); невозможно проверить обязательные API ТЦ
Back release: в составе релиза не найдено ни одной Story/Bug с заполненной КЭ сервиса
Back release: Zephyr не вернул ТЦ по ключу релиза HRPRELEASE-131571
Back release: для КЭ 'CoreTech(7993288)' (HRC-4360) отсутствует ТЦ Zephyr по маске 'HRPRELEASE-131571.CoreTech(7993288).api.Регресс'
Back release: для КЭ 'CoreTech(7993288)' есть Story с 'Новая функциональность' = 'Да', но отсутствует ТЦ Zephyr по маске 'HRPRELEASE-131571.CoreTech(7993288).api.НФ'
```

Предупреждения:

```text
Back release: нет задач со связью 'consist of' — проверка API ТЦ по КЭ пропущена
Back release: Zephyr временно не отдал ТЦ по ключу релиза HRPRELEASE-131571; проверка ТЦ пропущена, отсутствие ТЦ не зафиксировано как ошибка
```

## 9. Web release: обязательные ТЦ по КЭ

Проверка выполняется только для обычного релиза, не Hotfix, если у релиза есть лейбл `web`.

Для каждой КЭ сервиса из Story/Bug состава релиза проверяются:

- если внутри КЭ есть Story с `Новая функциональность = Да`, нужен `{ключ релиза}.{КЭ сервиса}.ipad/pwa/safari/sberbrowser.НФ`;
- для проекта `NEUROUI` у НФ нет PWA: `{ключ релиза}.{КЭ сервиса}.ipad/safari/sberbrowser.НФ`;
- всегда нужны регресс-ТЦ:
  - `{ключ релиза}.{КЭ сервиса}.ipad.Регресс`;
  - `{ключ релиза}.{КЭ сервиса}.pwa.Регресс`;
  - `{ключ релиза}.{КЭ сервиса}.safari.Регресс`;
  - `{ключ релиза}.{КЭ сервиса}.sberbrowser.Регресс`;
- для проекта `NEUROUI` регресс PWA не требуется.

Успех:

```text
Web release: для КЭ 'SmartProfile(2295205)' найден ipad Регресс ТЦ [HRPQA-C133028] 'HRPRELEASE-130030. SmartProfile(2295205). iPad. Регресс' ✓
Web release: для КЭ 'HRP.CoreUI-Neuro(9644020)' найден iPad/Safari/SberBrowser НФ ТЦ [HRPQA-C133029] 'HRPRELEASE-131704. HRP.CoreUI-Neuro(9644020). iPad/Safari/SberBrowser. НФ' ✓
Web release: КЭ 'HRP.CoreUI-Neuro(9644020)' относится к NEUROUI — PWA ТЦ не требуется ✓
```

Ошибки:

```text
Web release: Zephyr не вернул ТЦ по ключу релиза HRPRELEASE-130030
Web release: для КЭ 'SmartProfile(2295205)' есть Story с 'Новая функциональность' = 'Да', но отсутствует ТЦ Zephyr по маске 'HRPRELEASE-130030.SmartProfile(2295205).ipad/pwa/safari/sberbrowser.НФ'
Web release: для КЭ 'SmartProfile(2295205)' (SFILE-11765, SFILE-11771) отсутствует ТЦ Zephyr по маске 'HRPRELEASE-130030.SmartProfile(2295205).ipad.Регресс'
```

Предупреждение:

```text
Web release: Zephyr временно не отдал ТЦ по ключу релиза HRPRELEASE-130030; проверка ТЦ пропущена, отсутствие ТЦ не зафиксировано как ошибка
```

## 10. Zephyr: проверки найденных ТЦ

Для каждого обязательного ТЦ, найденного в back/web-проверках, дополнительно проверяется:

- поле ТЦ `Вид тестирования`;
- все ТК внутри ТЦ находятся в статусе `Approved`.

Если ТЦ найден по маске `.НФ`, ожидается `Вид тестирования = НФ`.
Если ТЦ найден по маске `.Регресс`, ожидается `Вид тестирования = Регресс`.

Успех:

```text
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': Вид тестирования = 'Регресс' ✓
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': все ТК внутри ТЦ в статусе 'Approved' ✓
```

Ошибки:

```text
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': не удалось получить детали ТЦ для проверки поля 'Вид тестирования'
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': поле 'Вид тестирования' не найдено, ожидается 'Регресс'
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': 'Вид тестирования' = 'НФ', ожидается 'Регресс'
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': не удалось получить детали ТЦ для проверки статусов ТК
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': внутри ТЦ не найдены ТК
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': ТК [HRPQA-T12345] 'Проверка профиля' не в статусе 'Approved' (текущий: 'Draft')
```

Предупреждения:

```text
ТЦ 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': нет key, невозможно проверить поле 'Вид тестирования'
ТЦ 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': нет key, невозможно проверить статусы ТК внутри ТЦ
ТЦ [HRPQA-C133028] 'HRPRELEASE-130030.SmartProfile.iPad.Регресс': не удалось получить детали ТК: HRPQA-T12345
```

## 11. Баги

Проверяются задачи типов `Bug`, `Defect`, `Ошибка` из состава релиза.

Общие проверки для всех релизов:

- обязательный лейбл контура `web`/`back`/`mobile`;
- статус бага;
- описание;
- старый контурный лейбл: один из `sigma`, `cloud`, `mobile`;
- метод обнаружения, если стенд не `ПСИ`, `ПРОМ`, `ПРОМ (Stand-in)`;
- для ПРОМ-багов обязательна заполненная причина пропуска (`customfield_16801`);
- если стенд `ПРОМ` или `ПРОМ (Stand-in)`, баг дополнительно проверяется в Confluence.

Статус:

- обычный релиз: `закрыт` или `closed`;
- Hotfix: `подтверждение исправления`.

Успех:

```text
Bug в статусе 'Closed' ✓
Hotfix: Bug в статусе 'Подтверждение исправления' ✓
```

Ошибки:

```text
Bug в статусе 'In Progress', ожидается один из: 'closed', 'закрыт'
Hotfix: Bug в статусе 'Closed', ожидается 'подтверждение исправления'
Отсутствует описание
Отсутствует лейбл контура. Должен быть один из: sigma, cloud, mobile
Некорректный метод обнаружения: 'Code Review'. Стенд: 'IFT'
ПРОМ Bug: поле 'Причина пропуска' (customfield_16801) не заполнено
ПРОМ Bug: поле 'Причина пропуска' (customfield_16801) = 'Другое', содержит недопустимые значения: другое. Допустимо: ...
Ошибка поиска багов: <текст ошибки>
```

Предупреждение:

```text
Баги не найдены в составе релиза
```

## 12. Hotfix-проверки багов

Для Hotfix дополнительно проверяется:

- `customfield_11507` / этап обнаружения = `ПРОМ`;
- приоритет = `Blocker` / `Блокирующий` или `Critical` / `Критичный`.

Ошибки:

```text
Hotfix: Этап обнаружения (customfield_11507) = 'IFT', ожидается 'ПРОМ'
Hotfix: Приоритет = 'Major', ожидается Блокирующий (Blocker) или Критичный (Critical)
```

## 13. Confluence для ПРОМ-багов

Для багов со стендом `ПРОМ` или `ПРОМ (Stand-in)` проверяется, не встречается ли ключ бага на дочерних страницах Confluence по проектной области.

Ошибка:

```text
Баг найден на Confluence: [SFILE bugs|https://confluence.sberbank.ru/pages/viewpage.action?pageId=123456]
```

Ошибка проверки:

```text
Ошибка проверки Confluence: <текст ошибки>
```

## 14. Story: обязательные поля и описание

Для Story из состава релиза проверяется:

- обязательный лейбл контура `web`/`back`/`mobile`;
- описание;
- `customfield_24000` / `Новая функциональность`: `Да` или `Нет`;
- `customfield_18400` / `Требуется НТ`: `Да` или `Нет`;
- `customfield_10006` / Epic Link.

Успех:

```text
Story: описание заполнено ✓
Story: Новая функциональность = Да ✓
Story: Требуется НТ = Нет ✓
Story: Epic Link = HRC-123 ✓
```

Ошибки:

```text
Story: отсутствует описание
Story: Поле 'Новая функциональность' (customfield_24000) не заполнено
Story: Поле 'Новая функциональность' (customfield_24000) содержит недопустимое значение 'Maybe'. Допустимо: 'Да' / 'Нет'
Story: не заполнен Epic Link (customfield_10006)
Ошибка поиска Story задач: <текст ошибки>
```

Информационный вывод:

```text
Story задачи не найдены в составе релиза
```

## 15. Story: блок требований и архитектуры

По API читается `customfield_21100`.
HTML целиком не сравнивается: из поля извлекаются строки блока.

Проверяется:

- `Бизнес-требования` = `Зафиксировано` и есть ссылка;
- `Функциональное решение` = `Зафиксировано` и есть ссылка;
- `Архитектура` = `Не меняется` или `Утверждена`.

Для архитектуры:

- если `Архитектура = Не меняется`, поле `customfield_23700` / `Архитектурные изменения` должно быть `Не влияет на архитектуру`;
- если `Архитектура = Утверждена`, должна быть ссылка и поле `Архитектурные изменения` должно быть заполнено допустимым значением из списка архитектурных изменений.

Успех:

```text
Story: Бизнес-требования зафиксированы, ссылка есть ✓
Story: Функциональное решение зафиксированы, ссылка есть ✓
Story: Архитектура не меняется, влияние на архитектуру заполнено корректно ✓
Story: Архитектура утверждена, ссылка и влияние на архитектуру корректны ✓
```

Ошибки:

```text
Story: в customfield_21100 не найдена строка 'Бизнес-требования'
Story: Бизнес-требования = 'Не найдено', ожидается 'Зафиксировано'
Story: Бизнес-требования = 'Зафиксировано', но ссылка не указана
Story: в customfield_21100 не найдена строка 'Функциональное решение'
Story: Функциональное решение = 'Не найдено', ожидается 'Зафиксировано'
Story: Функциональное решение = 'Зафиксировано', но ссылка не указана
Story: в customfield_21100 не найдена строка 'Архитектура'
Story: Архитектура = 'Не меняется', но поле 'Архитектурные изменения' = 'None'. Ожидается 'Не влияет на архитектуру'
Story: Архитектура = 'Утверждена', но ссылка не указана
Story: Архитектура = 'Утверждена', но поле 'Архитектурные изменения' = 'None'. Ожидается одно или несколько архитектурных изменений
Story: Архитектура = 'Утверждена', но поле 'Архитектурные изменения' = 'Не влияет на архитектуру'. Значение 'Не влияет на архитектуру' допустимо только для статуса 'Не меняется'
Story: Архитектура = 'Утверждена', но поле 'Архитектурные изменения' = 'abc' содержит недопустимые значения: abc
Story: Архитектура = 'Не найдено', ожидается 'Не меняется' или 'Утверждена'
```

Если блок требований/архитектуры невалиден, а Story уже в `Ready for UAT`, `UAT` или `Done`, добавляется отдельная ошибка:

```text
Story испорчена и влияет на метрику модели зрелости: проверка блока требований/архитектуры не выполнена, текущий статус 'Ready for UAT'
```

## 16. Story: порядок привязки требований и архитектуры

По changelog проверяется, что `customfield_21100` и `customfield_23700` не менялись после перехода в статусы:

- `ready for uat`;
- `uat`;
- `done`.

Ошибка:

```text
Story: поле 'Бизнес-требования / Функциональное решение / Архитектура' было изменено после перехода в 'Ready for UAT' (2026-07-08 15:30). Требования и архитектура должны быть привязаны до UAT/Done
Story: поле 'Архитектурные изменения' было изменено после перехода в 'UAT' (2026-07-08 16:10). Требования и архитектура должны быть привязаны до UAT/Done
```

Предупреждение:

```text
Story: не удалось получить changelog для проверки порядка привязки требований: <текст ошибки>
```

## 17. Story: время в тест-статусах

Для проектных областей, у которых задан норматив, считается суммарное время Story в статусах:

- `READY FOR IFT`;
- `IFT`;
- `READY FOR UAT`;
- `UAT`.

Допустимая вилка: от 90% до 110% норматива.

Успех:

```text
Story: время в тест-статусах 2.1 д. в пределах 90–110% норматива (1.8–2.2 д.) ✓
```

Ошибки:

```text
Story: суммарное время в тест-статусах (3.2 д.) больше 110% норматива (2.2 д. из 2.0 д.) для проектной области HRC
Story: суммарное время в тест-статусах (1.0 д.) меньше 90% норматива (1.8 д. из 2.0 д.) для проектной области HRC
```

Предупреждение:

```text
Story: не удалось получить changelog для проверки времени в статусах: <текст ошибки>
```

## 18. Task внутри Story

Для Task, связанных со Story через `consist of` / `is part of`, проверяется:

- Task должна быть закрыта;
- если Task в той же проектной области, что и Story, должен быть заполнен Epic Link.

Закрытые статусы учитываются без регистра:

- `closed`;
- `закрыта`;
- `закрыто`;
- `resolved`;
- `решена`;
- `решено`;
- `cancelled`;
- `отменён`;
- `отменен`.

Успех:

```text
Task внутри Story [HRC-4316] закрыта ✓
Task внутри Story [HRC-4316]: Epic Link = HRC-123 ✓
```

Ошибки:

```text
Task внутри Story [HRC-4316] не закрыта. Текущий статус: 'In Progress'
Task внутри Story [HRC-4316]: не заполнен Epic Link (customfield_10006)
Ошибка проверки Task HRC-5000: <текст ошибки>
```

## 19. Обязательный Pull Request

Для каждой Story/Bug/Defect/Ошибка в составе релиза должен быть найден Pull Request.

Для Story проверяется только сама Story. PR в Task внутри Story не засчитывается для этой проверки.
Для Bug/Defect/Ошибка проверяется сама задача.

Алгоритм поиска сначала использует основной рабочий вариант dev-status, затем fallback-варианты:

- dev-status `pullrequest`;
- dev-status `repository`;
- Jira remote links;
- Jira issue properties;
- raw/rendered fields;
- comments;
- browse HTML.

Успех:

```text
Pull Request найден в HRC-4360 (dev-status stash/repository) ✓
```

Ошибка:

```text
Pull Request не найден. Для каждой Story/Bug в составе релиза должен быть PR на самой задаче
```

Предупреждение:

```text
Pull Request: не удалось проверить HRC-4360: <текст ошибки>
```

## 20. AIFIXED по GigaCode

Проверка отдельная от обязательного PR/commit.

Если в PR/commit Story/Bug/Defect/Ошибка или Task внутри Story найден маркер GigaCode, на главную Story/Bug добавляется лейбл `AIFIXED`.

Распознаваемые маркеры:

- `#GigaCode Agent`;
- `#gigacode agent`;
- `Co-authored-by: GigaCode Assistant`;
- `Co-authored-by: GigaCode`;
- `Co-authorer-by: GigaCode Assistant`;
- `Co-authorer-by: GigaCode`;
- варианты с markdown-ссылкой вокруг email.

Успех:

```text
AIFIXED: GigaCode PR/commit не найден — лейбл AIFIXED не требуется ✓
GigaCode PR/commit найден в HRC-4360 (маркер: 'Co-authored-by: GigaCode Assistant, #GigaCode Agent'); лейбл AIFIXED добавлен ✓
GigaCode PR/commit найден в HRC-4360 (маркер: '#GigaCode Agent'); лейбл AIFIXED уже есть ✓
```

Ошибка:

```text
GigaCode PR/commit найден в HRC-4360 (маркер: '#GigaCode Agent'), но не удалось добавить лейбл AIFIXED: <текст ошибки>
```

Предупреждение:

```text
AIFIXED: не удалось проверить HRC-4360: <текст ошибки>
```

## 21. Отлинкованные от релиза задачи и merged PR

По changelog релизного объекта проверяются задачи, которые были удалены из issue links релиза и сейчас не входят в состав релиза.

Для таких задач типов `Story`, `Task`, `Bug`, `Defect`, `Ошибка` проверяется dev-status:

- если отлинкованная задача связана с любой Story/Bug/Defect/Ошибка, которая сейчас есть в составе релиза, проверка merged PR пропускается;
- если у отлинкованной задачи есть лейбл `review_confirmed`, проверка merged PR пропускается;
- если найден PR в статусе `merged`, это ошибка;
- если merged PR не найден, проверка считается успешной.

Успех:

```text
Отлинкованная от релиза задача связана с задачей/багом в составе релиза (HRC-4360) — проверка merged PR пропущена ✓
Отлинкованная от релиза задача имеет лейбл review_confirmed — проверка merged PR пропущена ✓
Отлинкованная от релиза задача: merged PR не найден ✓
```

Ошибка:

```text
Отлинкованная от релиза задача содержит PR в статусе merged (dev-status stash/pullrequest: 12345 (merged)). Если PR уже влит, задача/баг не должна быть отлинкована от релизного объекта
```

Предупреждения:

```text
Отлинкованные задачи: не удалось получить changelog релиза для проверки merged PR: <текст ошибки>
Отлинкованные задачи: не удалось получить задачи для проверки merged PR: <текст ошибки>
Отлинкованная задача: не удалось проверить статус PR: <текст ошибки>
```

## 26. Технические ограничения Zephyr

Zephyr-запросы ограничены настройками:

- `ZEPHYR_REQUEST_TIMEOUT_SECONDS`, по умолчанию `10`;
- `ZEPHYR_MAX_RETRIES_PER_REQUEST`, по умолчанию `3`;
- `ZEPHYR_MAX_FAILED_REQUESTS`, по умолчанию `20`.

При исчерпании лимита дальнейшие Zephyr-проверки останавливаются, чтобы скрипт не зависал.

Примеры сообщений:

```text
Zephyr API: лимит неуспешных запросов исчерпан (20/20), дальнейшие Zephyr-запросы остановлены
Zephyr: лимит неуспешных запросов исчерпан, дальнейшая проверка ТК пропущена
```
